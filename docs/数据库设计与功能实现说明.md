# 第一部分 · 数据库设计

## 1.0 为什么是 7 个库

传统单体项目一个库搞定。这个项目是微服务（micro service，一个业务域单独起一个进程），所以**一个服务独占一个 MySQL 库**：

| 库 | 归属服务 | 端口 | 存什么 |
|---|---|---|---|
| `yd_user` | fitness-user | 8101 | 账号、站内消息 |
| `yd_course` | fitness-course | 8102 | 课程、门店、场次、秒杀活动、优惠券、视频与进度 |
| `yd_order` | fitness-order | 8103 | 预约订单（含秒杀单） |
| `yd_point` | fitness-point | 8104 | 积分账户、积分流水、兑换商品 |
| `yd_behavior` | fitness-behavior | 8106 | 行为埋点明细 |
| `yd_community` | fitness-community | 8105 | 动态、评论、点赞、关注 |
| `yd_admin` | fitness-admin-server | 8107 | 管理员账号、操作日志 |

这么拆的**代价**是：跨库不能 JOIN，不能靠外键（Foreign Key，数据库级别的关联校验）保证数据一致。
这么拆的**收益**（也是这个项目真正的学习价值）：逼你使用分布式环境下的三件标准武器——

1. **冗余快照**：把需要展示的名字直接复制存一份到自己的表里（下文反复出现）；
2. **Feign 调用**（远程方法调用，像调本地方法一样调另一个服务的 HTTP 接口）：需要实时结果时用，比如订单服务占课程名额；
3. **MQ 事件**（Message Queue，消息队列，A 服务扔一条消息就走，B 服务自己消费）：不需要实时结果时用，比如完课加积分。

全项目 SQL 里**一个 `FOREIGN KEY` 都没有**，表之间的关联全靠业务字段 + 代码保证。这是微服务的常规做法（阿里 Java 开发手册也禁止用外键），面试被问要能答出理由。

建表脚本在 `fitness-backend/sql/`，9 个文件：

```
yd_user.sql  yd_course.sql  yd_order.sql  yd_point.sql  yd_behavior.sql
increment_1_community_message.sql   社区库 + 站内消息表
increment_1_schedule_verify.sql     课程场次表 + 订单加核销字段
increment_2.sql                     优惠券 / 关注 / 积分商城 / 管理员库
increment_3.sql                     视频进度表加防刷字段
```

`increment_*` 是「增量脚本」：项目已经跑起来了，新功能不能重建库，就在老库上 `ALTER`/`CREATE TABLE` 补一刀。思路对的（比 Flyway 那种自动化迁移工具朴素），**但有个真实的坑**：`docker/docker-compose.middleware.yml` 把整个 `sql/` 挂进 MySQL 的初始化目录，MySQL 按**文件名字母序**执行，于是 `increment_1_*`/`increment_2` 会排在 `yd_course.sql`/`yd_order.sql` 前面跑，`ALTER TABLE t_booking` 时表还不存在 → 全新volume初始化直接失败。这个必须修（见第三部分 P0-8）。

## 1.1 yd_user

### t_user —— 用户表

| 字段 | 类型 | 含义 | 设计说明 |
|---|---|---|---|
| `id` | BIGINT AI | 主键 | 自增。全站对外的用户标识，JWT 里装的就是它 |
| `phone` | VARCHAR(11) | 手机号，登录账号 | **`UNIQUE KEY uk_phone`**，见下方"并发注册" |
| `password` | VARCHAR(100) | BCrypt 散列 | 不存明文。100 而非 60 是留余量（BCrypt 实际 60 字符） |
| `nickname` | VARCHAR(20) | 昵称 | 注册时代码自动生成 `"悦动同学" + 手机号后4位` |
| `avatar_color` | VARCHAR(2) | **头像配色下标 0~5** | 见下方讲解 ① |
| `status` | TINYINT | 1 正常 / 0 禁用 | 管理端可禁用用户。登录时校验，禁用返回 `USER_DISABLED` |
| `created_at` | DATETIME | 注册时间 | `DEFAULT CURRENT_TIMESTAMP`，DB 自动填 |
| `updated_at` | DATETIME | 更新时间 | `ON UPDATE CURRENT_TIMESTAMP`，DB 自动刷新 |

索引：`PRIMARY KEY(id)` + `uk_phone(phone)`。

**讲解 ①：`avatar_color` 为什么只存一个数字**

前端没有真实图片上传（也没有 OSS 对象存储），头像是**用纯色底 + 首字母**渲染出来的。项目里定义了 6 种渐变色（`fitness-web/src/constants.js` 的 `AVATAR_COLORS`），所以库里只需要存"用第几号色"。VARCHAR(2) 存 `'0'`~`'5'`。

- 好处：零图片存储成本、加载快、UI 统一。
- 代价：这不是真实项目的做法。真实项目这里是 `avatar_url VARCHAR(200)` + 对象存储。当前设计是「演示用简化」，代码注释里也这么写的。
- 注意它**跨库被复制**了：`t_post.avatar_color` 存了作者当时的配色（快照）。

**讲解 ②：并发注册靠什么防重复**

代码里先 `selectCount` 查手机号存不存在，再 `insert`。两个请求同时进来，都查到"不存在"，于是都要插——**这就是经典并发问题**。兜底的是 `uk_phone` 唯一索引：第二条 `insert` 会抛 `DuplicateKeyException`，代码捕获后返回"手机号已注册"。

这就是「**先查再插永远不是原子操作，唯一索引才是最终防线**」的标准范式。项目里这个模式出现了至少 4 次（注册、视频进度、点赞、积分账户初始化），值得单独记住。

### t_message —— 站内消息表（increment_1 新增）

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | BIGINT AI | 主键 |
| `user_id` | BIGINT | 接收人（逻辑外键 → t_user.id） |
| `title` | VARCHAR(50) | 消息标题 |
| `content` | VARCHAR(200) | 消息内容 |
| `msg_type` | VARCHAR(20) | `BOOKING` 预约 / `POINT` 积分 / `INTERACTION` 互动 |
| `is_read` | TINYINT | 0 未读 1 已读 |
| `created_at` | DATETIME | 时间 |

索引 `idx_user_read(user_id, is_read, created_at)`：这是**覆盖「查我的未读消息并按时间倒序」这一条查询**的复合索引。字段顺序有讲究——先等值条件（user_id、is_read）再排序条件（created_at），顺序反了就用不上索引排序。

**这张表为什么存在别的服务的写法里**：消息是「谁的通知发给谁」，属于用户域，所以落在 yd_user。但产生通知的是订单/积分/社区三个服务，它们不直接写这张表（跨库写不了），而是各发一条 RabbitMQ 消息到 `ex.notify.exchange`，由 user 服务的 `NotifyEventConsumer` 消费后落库。**这是"写操作收口到数据owner"**，微服务里的常规做法。

⚠️ 已知缺陷：网关 `application.yml` 的路由表里**没有 `/api/message/**`**，所以消息中心 4 个接口通过网关访问不到（见第三部分 P0-7）。

## 1.2 yd_course（最复杂的库，8 张表）

### t_store —— 门店表

| 字段 | 类型 | 含义 | 设计说明 |
|---|---|---|---|
| `id` | BIGINT AI | 主键 | |
| `name` | VARCHAR(50) | 门店名 | |
| `lng` / `lat` | DECIMAL(10,6) | 经度 / 纬度 | **DECIMAL 而不是 DOUBLE**：浮点数有精度误差，6 位小数约 0.1 米。见讲解 ③ |
| `address` | VARCHAR(100) | 地址文案 | |
| `rating` | DECIMAL(2,1) | 评分，如 4.9 | 演示数据手写，不是真实算出来的均值 |
| `tags` | VARCHAR(100) | 特色标签，**逗号分隔** | 见讲解 ④ |
| `open_hours` | VARCHAR(20) | 营业时间文案 | 如 `'07:00-23:00'`、`'24 小时'` |
| `phone` | VARCHAR(20) | 电话 | |
| `coaches` | INT | 教练数 | 纯展示，没有教练表 |

**这张表没有索引**（除主键）。门店只有 4 条，无所谓。

**讲解 ③：为什么经纬度/金额一律 DECIMAL 不用 DOUBLE**

`0.1 + 0.2 == 0.3` 在 IEEE-754 浮点（float/double）里是 `false`（实际得 `0.30000000000000004`）。金额计算用 double 会出现「差一分钱对不上账」，所以 Java 里金额用 `BigDecimal`、MySQL 里用 `DECIMAL(p,s)`。`p` 是总位数，`s` 是小数位，`DECIMAL(10,2)` 最大 99999999.99。这是硬规范，面试常问。

**讲解 ④：`tags`、`images` 为什么用逗号分隔字符串而不是建关联表**

规范做法是 `t_tag` + `t_course_tag` 多对多关联。项目这里直接 `VARCHAR(100)` 存 `'燃脂,新手友好'`，代码用 `String.split(",")` 还原成列表。

- 为什么可以：标签在这里**只用于展示**，不参与精确检索（搜索是 `LIKE '%关键字%'` 模糊匹配整串）。
- 为什么不规范：`LIKE '%燃脂%'` **无法走索引**（前导通配符），数据量大就是全表扫描；也无法做"按标签聚合统计"。
- 结论：演示项目从简是合理的，但要能说清代价。真实项目要改成「冗余展示字段 + ES 或标签关联表做检索」。

**讲解 ⑤：`type` 为什么存中文而不是枚举编码**

常见规范是存 `TINYINT` + 字典表。这里直接存 `'团课'`，好处是 SQL 肉眼可读、代码不用翻译；代价是改一个字（"团课"→"团操"）就得刷全表，且索引里存的是字符串（占空间、比较慢）。演示项目可接受，**但面试要能指出这个取舍**。

**讲解 ⑥：`booked` 这种"计数列"的设计与风险**

「一个课程约了多少人」本质是 `SELECT COUNT(*) FROM t_booking WHERE course_id=?`。但订单在**另一个库**（yd_order），跨库根本 COUNT 不了；而且每次查详情都 COUNT 一遍太慢。所以课程库里冗余一个 `booked` 计数，由订单服务通过 Feign 调 `/inner/course/occupy` 来 `+1`、`/inner/course/release` 来 `-1`。

关键实现（`fitness-course/.../mapper/CourseMapper.java`）：

```sql
-- 占用：把"判断满员"和"+1"合并成一条原子 UPDATE
UPDATE t_course SET booked = booked + 1, updated_at = NOW()
 WHERE id = #{courseId} AND status = 1 AND booked < capacity
-- 释放
UPDATE t_course SET booked = booked - 1 WHERE id = #{courseId} AND booked > 0
```

- **为什么这样写能防超卖**：MySQL 的 `UPDATE` 会对行加排他锁（X 锁），`booked < capacity` 这个条件和 `+1` 在同一个语句里执行，不存在"两个线程都读到 19 然后都写成 20"的窗口。Java 侧只看**影响行数**（返回 1 = 占到，返回 0 = 没位了）。这叫 **CAS（Compare-And-Swap，比较并交换）思想落到 SQL 上**。
- **风险**：`booked` 和真实订单数会**漂移**。代码里释放名额的调用不检查返回值、也没有幂等令牌（比如"这个订单号只能释放一次"），一旦重复调用就凭空多出一个空位。这类"计数列"要靠定期对账任务修正，项目里没有对账任务。
- `booked > 0` 这个守卫只防负数，不防"把别人的位子释放掉"。

**讲解 ⑦：`next_time` 和 `t_course_schedule` 的关系（一个真实的遗留问题）**

`t_course_schedule`（场次表）是**后来增量加的**（`increment_1_schedule_verify.sql`），加了之后"什么时候上课"应该以场次的 `schedule_time` 为准。但 `t_course.next_time` 这个字符串字段（值像 `'今天 19:00'`、`'预约制'`）没删掉，而且**还在被使用**：

- 课程列表 VO 仍然返回 `nextTime`（前端展示）；
- 秒杀建单时，订单的 `book_time` 取的是 `course.getNextTime()`（`SeckillCreateConsumer`），而普通预约取的是 `schedule.getScheduleTime()` 格式化后的值。

结果：秒杀单上显示的"上课时间"可能是 `'预约制'` 这种文案，不是时间。**这是前端 Mock 阶段留下的字段，加场次表时没同步清理**，属于我建议你改的项（第三部分 P1-3）。

### t_course_schedule —— 场次表（increment_1 新增）

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | BIGINT AI | 场次 id |
| `course_id` | BIGINT | 所属课程 |
| `schedule_time` | DATETIME | 真实上课时间 |
| `capacity` | INT | **本场**容量 |
| `booked` | INT | **本场**已约 |
| `status` | TINYINT | 1 可约 0 已取消 |

索引 `idx_course_time(course_id, schedule_time)`：查"某门课未来的场次并按时间排"。

种子数据用一句 SQL 给每门在售课程生成 3 个场次，时间相对 `NOW()` 偏移，**保证演示永不过期**：

```sql
INSERT INTO t_course_schedule (course_id, schedule_time, capacity, booked)
SELECT c.id, DATE_ADD(NOW(), INTERVAL (c.id * 10 + s.n) HOUR), c.capacity,
       LEAST(FLOOR(c.capacity * 0.6), c.capacity - 1)
FROM t_course c JOIN (SELECT 1 AS n UNION SELECT 2 UNION SELECT 3) s
WHERE c.status = 1;
```

（`(SELECT 1 AS n UNION SELECT 2 UNION SELECT 3)` 是一个只有 1 列 3 行的临时表，用来做"乘 3 倍"的笛卡尔展开——这个技巧值得学。）

**两层容量的问题**：`t_course.capacity` 和 `t_course_schedule.capacity` 同时存在。普通预约走 `occupySchedule`（改场次表），秒杀和旧接口走 `occupy`（改课程表）——**同一门课两个口径的余位，互不影响**。这必然导致"课程显示还有位，点进去场次已满"或反之。建议要么统一到场次（`t_course.booked/capacity` 变成场次的汇总视图，由代码维护），要么彻底删掉课程层容量。

### t_seckill_activity —— 秒杀活动表

| 字段 | 类型 | 含义 | 设计说明 |
|---|---|---|---|
| `id` | BIGINT AI | 主键 | |
| `course_id` | BIGINT | 秒杀哪门课 | |
| `seckill_price` | DECIMAL(10,2) | 秒杀价 | 与 `t_course.price` 并存 → 订单要知道用的是哪个价 |
| `total` | INT | 总名额 | 发放量，建活动后不改 |
| `remain` | INT | **DB 剩余名额** | 与 Redis 库存成双写，见讲解 ⑧ |
| `start_time`/`end_time` | DATETIME | 活动起止 | |
| `status` | TINYINT | 0 待开始 / 1 进行中 / 2 已结束 | 见讲解 ⑨ |

索引 `idx_status(status)`：定时任务扫"待开始/进行中"。

**讲解 ⑧：`remain`（DB）与 `seckill:stock:{id}`（Redis）为什么要两份库存**

秒杀的本质矛盾是：DB 抗不住瞬时几千 QPS，Redis 抗得住但重启会丢。项目的解法：

1. 活动开始前，定时任务（`SeckillActivityServiceImpl.scanAndSwitch()`，`@Scheduled(fixedDelay=30_000)`）扫表，把 `remain` **预热**写进 Redis `seckill:stock:{activityId}`；
2. 抢购时**只碰 Redis**，一条 Lua 原子完成"判库存 + 判一人一单 + 扣减 + 记资格"；
3. 抢到之后异步建单，消费者建单成功才 `deductRemain` 把 DB 的 `remain` 减 1。

所以 Redis 是**抢的依据**，DB 是**账本**。两者会有短暂差值（消息还在队列里时 Redis 已扣、DB 未扣），这是最终一致性的正常形态。

**讲解 ⑨：`status` 三态由谁推进**

`scanAndSwitch()` 每 30 秒扫表：到 `start_time` 的 → `status=1` 并预热库存；过了 `end_time` 的 → `status=2`。管理端 `adminEnd` 也能手动置 2。

⚠️ 两个真实问题：①**没有分布式锁**，起两个实例就会有两个节点同时扫到并同时预热（幂等还好，但状态机会重复翻转）；② 种子数据里三个活动的 `status` 全写死 `0` 而 `start_time` 是昨天，**依赖定时任务把它推成 1**——服务一起来等 30 秒才有秒杀，这解释了"为什么我一启动没有秒杀活动"。

### t_video / t_video_progress —— 跟练视频与进度

`t_video`：`id, title, coach, duration(分钟), level(难度), calories, plays(跟练人数), url`。

⚠️ `url` 注释写着 "Mock 为空"，且 `VideoVO` **没有 url 字段** → 接口根本没法把可播放地址给前端。所以前端的"播放器"是假的（用进度条模拟）。这是当前一个功能空洞（第三部分 P1-6）。

`t_video_progress`：

| 字段 | 类型 | 含义 | 设计说明 |
|---|---|---|---|
| `id` | BIGINT AI | 主键 | |
| `user_id`/`video_id` | BIGINT | 谁、哪个视频 | **`UNIQUE KEY uk_user_video`** |
| `progress` | INT | 最大进度 0~100 | 注意语义是"看过的最大值"，不是当前值 |
| `finished` | TINYINT | 是否完课 | ⚠️ 实际永远为 0，见第三部分 P0-3 |
| `last_report_at` | DATETIME | 上次上报时间 | increment_3 加的，防刷用 |
| `updated_at` | DATETIME | | |

**讲解 ⑩：`progress` 为什么必须是"最大值"而不是"最新值"**

用户会从视频中间拖进度条，也可能只看 30% 就退出后再看 20%。如果 `progress` 存最新值，往回拖就把学习记录改小了，完课判定会乱。所以 Mapper 里写的是**带条件的单调更新**（`VideoProgressMapper.advance`）：

```sql
UPDATE t_video_progress SET progress = #{newProgress}, ...
 WHERE user_id = ? AND video_id = ? AND progress < #{newProgress}
```

`WHERE progress < newProgress` 一句保证进度只增不减。这也是 CAS 思路。

**防刷**（`VideoServiceImpl.reportProgress()`）：用 `last_report_at` 算出两次上报的时间差，要求 `新增进度 ≤ 经过秒数 × 1.5 + 15`（15 秒宽容），否则拒绝。即"你不可能 10 秒内看完 5 分钟视频"。这是很实用的接口防刷例子。

### t_coupon / t_user_coupon —— 优惠券

`t_coupon`：

| 字段 | 类型 | 含义 | 设计说明 |
|---|---|---|---|
| `id` | BIGINT AI | 主键 | |
| `title` | VARCHAR(50) | 券名 | 如 '新人立减券' |
| `threshold` | DECIMAL(10,2) | **使用门槛**：满 X 元可用，0 = 无门槛 | |
| `discount` | DECIMAL(10,2) | 抵扣金额 | 满减券，不是折扣券 |
| `total` / `remain` | INT | 发放总量 / 剩余可领 | 与秒杀同构的双份库存 |
| `limit_per_user` | INT | 每人限领 | 注释直说"当前实现固定 1" |
| `start_time` / `end_time` | DATETIME | 可领起止 | `end_time` **同时是使用截止**，一字段两用（简化，真实项目要拆开） |
| `status` | TINYINT | 1 上架 / 0 下架 / 2 作废 | |

`t_user_coupon`：`id, user_id, coupon_id, status(UNUSED/USED), order_no, received_at, used_at`，索引 `uk_user_coupon(user_id, coupon_id)` + `idx_user_status(user_id, status)`。

**讲解 ⑪：为什么"领到的券"要单独一张表，而不是只在 t_coupon 上记谁领了**

`t_coupon` 是**券的模板/活动**（一类券），`t_user_coupon` 是**某人手里的一张券**（一个实例）。这是"模板 - 实例"分离，和电商的"商品 - 订单商品行"一个道理。

两个关键点：
- `uk_user_coupon(user_id, coupon_id)` = 一人一券的**数据库级**保证（前面讲过的"唯一索引兜底"）。
- **`t_user_coupon.order_no` 是跨库关联**：券在 yd_course 库，订单在 yd_order 库，靠**订单号字符串**把它们连起来。所以 `order_no`（而非 `id`）才是要对外传播的标识——见讲解 ⑬。

**领取的实现**（`CouponServiceImpl.receive()` + `fitness-course/src/main/resources/lua/coupon_receive.lua`）：和秒杀 Lua **完全同构**，库存 DECR + Set 记资格 + 按领取截止时间自动过期：

```lua
if tonumber(redis.call('GET', KEYS[1]) or '0') <= 0 then return 1 end   -- 已抢完
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return 2 end     -- 重复领取
redis.call('DECR', KEYS[1]); redis.call('SADD', KEYS[2], ARGV[1])
redis.call('EXPIRE', KEYS[1], tonumber(ARGV[2])); redis.call('EXPIRE', KEYS[2], tonumber(ARGV[2]))
return 0
```

**为什么必须在 Lua 里做**（这是核心知识点）：如果 Java 里分三步 `GET` → 判断 → `DECR`，两个线程可以同时读到 `remain=1` 然后各自扣减，库存就变负数了。Lua 脚本在 Redis 里**单线程整体执行完**，中间不会被别的命令插进去，所以"检查 + 扣减"是一个不可分割的动作。同理，`SISMEMBER` 和 `SADD` 必须在同一个脚本里，否则两个人能同时通过"我没领过"的检查。

⚠️ 注意：领券后端把 `t_coupon.remain` 的 DB 侧写入做了吗？`preheat()` 只写 Redis，DB 的 `remain` 扣减在领取成功后同步做——所以券的库存是"Redis 抢 + DB 立即落"，比秒杀少一层异步，一致性更好。

| `cancel_reason` | VARCHAR(50) NULL | 取消原因 | |
| `created_at` / `pay_time` | DATETIME | 下单 / 支付时间 | |

索引：`uk_order_no`、`uk_verify_code`、`idx_user_status(user_id, status)`、`idx_course_user(course_id, user_id, status)`。

**索引逐个讲**（这块面试很爱问，项目里的用法刚好都是典型场景）：

- `idx_user_status(user_id, status)` → 服务「我的预约列表，可按状态筛选」。`user_id` 放最前是因为它**总是**出现；`status` 是可选等值条件。查"我的全部"时只用前缀也能命中（最左前缀原则）。
- `idx_course_user(course_id, user_id, status)` → 专门服务**同人同课去重**那一句 `WHERE user_id=? AND course_id=? AND status IN ('UNPAID','BOOKED')`。注意代码里的条件顺序是 user→course，而索引顺序是 course→user ——**顺序不影响命中**（优化器会调整，因为两个都是等值），但 `status IN(...)` 能继续用索引范围扫描。这是"为一条具体查询专门设计的索引"，比盲加索引好。
- `uk_verify_code` → 核销按码直查，天然唯一。

**讲解 ⑬：为什么要 `order_no`，不用 `id` 当对外单号**

1. `id` 是自增的，对外暴露会被推断出业务量（竞品知道你一天多少单）；
2. 跨库引用需要稳定字符串：券表要存"这张券核销在哪个订单上"，存 `id` 的话别的服务拿到 `id` 也拼不出可读单据，存 `order_no` 全局唯一且可展示；
3. 分库分表后自增 id 会冲突，业务单号不受影响。

生成方式（`BookingServiceImpl.genOrderNo()`）：`"B" + System.currentTimeMillis() + 随机100~999`。**这是个弱实现**：高并发下同一毫秒 + 随机数撞车的概率不低（900 个桶），撞了就被 `uk_order_no` 拒掉，但代码**没有重试**，直接报错给用户。真实项目用雪花算法（Snowflake：时间戳 + 机器号 + 序列号，趋势递增且分布式唯一）或 UUID。建议改（第三部分 P1-5）。

**讲解 ⑭：`activity_id` 非空 = 秒杀单，这个设计**

好处：一张表容纳两种订单，列表/详情/取消/核销逻辑全部复用，不用 UNION 两张表。
代价：秒杀单没有 `schedule_id`，**因此不走场次容量、也不受 15 分钟延迟取消的保护范围之外的差异**——秒杀单的价格来源、时间来源都和普通单不同（就是 `next_time` 那个坑）。更严谨的做法是加一个 `order_type` 显式字段，别靠"某字段是否为 NULL"来判断业务类型（NULL 语义在代码里很容易漏判）。

**讲解 ⑮：`book_time VARCHAR(20)` 是个妥协字段**

订单要展示"什么时候上课"。如果存 `DATETIME`，展示时要格式化，而且早期版本时间来自 `next_time` 文案（`'预约制'` 根本无法转成日期）。所以干脆存字符串。

代价：没法按时间范围查询订单、没法排序"即将开课"。加了场次表之后，正确做法是存 `schedule_id` + `DATETIME`，展示时格式化——现在 `schedule_id` 加了，但 `book_time` 仍是字符串。**这就是增量开发留下的技术债**：字段能兼容就没人肯删。

**讲解 ⑯：`status` 用 VARCHAR 存 'UNPAID'，`t_course.status` 用 TINYINT 存 1/0 —— 同一个项目两套风格**

这不是刻意设计，是不同阶段写的。两种都常见：

| | 字符串枚举名 | 数字码 |
|---|---|---|
| 可读性 | SQL 里一眼看懂 | 要查字典 |
| 空间 | VARCHAR(10) | TINYINT 1 字节 |
| 索引体积 | 大 | 小 |
| 扩展 | 加状态不改字段 | 加状态只加个码 |
| 风险 | 拼写错误（代码里是常量类 `BookingStatus` 统一，OK） | 语义漂移 |

项目里的**约定**：订单这种"状态多、要日志可读"的用字符串（有 `BookingStatus` 常量类 + `occupiesSlot()` 辅助方法，挺好）；上下架这种二值用 TINYINT；秒杀活动三态用 TINYINT。面试能说清"我为什么这么选"就行，最怕的是自己项目里混乱且说不出理由。

订单状态机（代码事实）：

```
        pay            verify(核销)
UNPAID ──────► BOOKED ──────────► FINISHED
   │              │
   │ cancel/超时   │ cancel
   ▼              ▼
CANCELED ◄────────┘
```

只有 `UNPAID`/`BOOKED` 占用名额（`BookingStatus.occupiesSlot()`），所以取消时判断这个才决定要不要释放名额。

## 1.4 yd_point

### t_member_points —— 积分账户（每用户一行）

| 字段 | 类型 | 含义 |
|---|---|---|
| `user_id` | BIGINT | **主键就是业务主键**（不是自增 id） |
| `balance` | INT | 积分余额 |
| `total_checkin` | INT | 累计打卡天数 |
| `continuous_days` | INT | 连续打卡天数 |
| `updated_at` | DATETIME | |

**讲解 ⑰：为什么这张表用 `user_id` 当主键，不用自增 id**

一对一关系（一个用户恰好一个积分账户），`user_id` 就是天然唯一键。再塞一个自增 id 属于冗余，而且查询永远是 `WHERE user_id=?`，用 `user_id` 做主键 = **聚簇索引直接命中**，省一次回表。InnoDB 里主键就是数据的存放顺序，把最高频查询条件当主键是标准优化。

**讲解 ⑱：`balance` 为什么不 `SUM(points_log)` 算出来**

流水表只增不改，算余额要扫全部历史流水，慢且不可扩展。所以「**流水是账本，汇总是缓存/物化结果**」：

- 每次变动同时写 `t_points_log`（明细，永不修改，用于展示和对账）和 `t_member_points.balance`（汇总，用于余额展示）；
- 汇总列必须用**SQL 原子自增**更新，而不是 Java 里 `getBalance()+10` 再 set 回去（后者是"读-改-写"三步，并发会丢）：

```sql
UPDATE t_member_points SET balance = balance + #{points},
       total_checkin = total_checkin + 1, continuous_days = #{continuousDays}
 WHERE user_id = #{userId}
```

- 扣减方向更要小心：兑换用 `WHERE user_id=? AND balance >= #{cost}`，影响行数 0 = 余额不足。这一句把"校验余额"和"扣减"合并成原子操作，和课程表 `booked < capacity` 是同一个套路。项目里这种写法出现了 5 处，是这套代码最值得学的一招。

⚠️ `continuous_days` 的**数据来源是 Redis Bitmap 算出来的**（见下），MySQL 只存快照。这带来一个真实风险：Redis 数据丢了，Bitmap 无从重建，而 `continuous_days` 会一直停留在最后一次的值，且当月打卡记录全部丢失——这是这个项目**最需要补的一个设计缺口**（第三部分 P0-5）。

### t_points_log —— 积分流水

| 字段 | 类型 | 含义 | 设计说明 |
|---|---|---|---|
| `id` | BIGINT AI | 主键 | |
| `user_id` | BIGINT | 谁 | |
| `title` | VARCHAR(50) | 流水标题，直接展示 | 如 '每日打卡'、'完课奖励' |
| `points` | INT | **变动值，正加负减** | 一张表同时记收支，靠符号区分 |
| `biz_type` | VARCHAR(20) | CHECKIN / COURSE_FINISHED / POST_PUBLISHED / EXCHANGE | 见讲解 ⑲ |
| `biz_id` | VARCHAR(64) NULL | **业务幂等 id** | 见讲解 ⑲ |
| `created_at` | DATETIME | | |

索引：**`uk_biz(biz_type, biz_id)`**（唯一！）+ `idx_user(user_id, created_at)`。

**讲解 ⑲：`biz_type + biz_id` 这个组合是本项目最精华的设计（幂等）**

MQ 消息**至少投递一次**（at-least-once），网络抖动、消费者崩溃重投都会导致同一条消息被处理两遍。如果每遍都加 30 积分，用户刷一下就是巨积分。

解法两层：
1. **快路径**：Redis `SETNX idempotent:msg:{eventId}`，TTL 24 小时。抢不到 key 说明处理过，直接 ack 跳过。
2. **最终防线**：`t_points_log` 的 `uk_biz(biz_type, biz_id)` 唯一索引。即使 Redis 挂了/过期了/并发穿透了，第二次 `insert` 会抛 `DuplicateKeyException`，代码捕获后按"已处理"正常 ack。

`biz_id` 里放什么，取决于业务是什么（这就是它设计成 `VARCHAR(64)` 而不是 `BIGINT` 的原因）：

| biz_type | biz_id 实际值 | 语义 |
|---|---|---|
| `COURSE_FINISHED` | 事件的 `eventId`（UUID） | 这个完课事件只算一次 |
| `CHECKIN` | `'2026-10-13'`（日期串） | 这一天只加一次分 |
| `EXCHANGE` | `giftId + ':' + System.currentTimeMillis()` | 每次兑换都不同 → 实际**起不到幂等作用**，只是为了让唯一索引不为 NULL |

**注意 `biz_type` 必须参与唯一键**：否则打卡的日期串 `'2026-10-13'` 和某个 eventId 撞了会误判。用 `(类型, 业务id)` 做复合唯一键是流水表的标准设计。

⚠️ 已知严重问题：`t_points_log.biz_id` 里塞的是**生产者每次新生成的 UUID**，`CourseEventPublisher` 每次 `UUID.randomUUID()`。所以"同一场完课"重复发两次事件时，两次 eventId 不同，两层幂等**都拦不住**，会重复加分。根因在生产端（`finished` 标志位从未被置 1），见第三部分 P0-3。

### t_gift —— 积分商城商品

`id, name, points_cost(所需积分), stock(库存), status`。种子 4 件商品。

**兑换的实现**（`GiftServiceImpl.exchange()`）是本项目里**唯一一处正经 `@Transactional`**：

```
1 校验商品上架且有库存
2 ensureMember(userId)          // 账户行不存在就建（DuplicateKey 忽略）
3 deductForExchange(userId, cost)  // CAS 扣积分，返回 0 → 余额不足
4 giftMapper.deductStock(giftId)   // UPDATE ... WHERE stock > 0，返回 0 → 抛异常
5 insert 流水(EXCHANGE, -cost)
6 站内通知
```

第 3、4 步同库（yd_point），所以一个本地事务就能保证「扣积分」和「扣库存」要么都成要么都回滚——**不需要分布式事务**。类注释里明确写了这个判断，这是加分项：能识别出"哪些操作在同一库里、根本不用扯 Seata 那些东西"。

⚠️ 但第 6 步通知在事务内发 MQ：如果事务随后回滚（当前代码没有，但改代码时容易引入），消息已经出去了。发消息进事务是常见隐患，严谨做法是事务提交后再发（`TransactionSynchronization` 或 outbox 表）。

## 1.5 yd_behavior

### t_behavior_log —— 行为日志明细

| 字段 | 类型 | 含义 | 设计说明 |
|---|---|---|---|
| `id` | BIGINT AI | 主键 | |
| `event_id` | VARCHAR(64) | 事件唯一 id | `UNIQUE KEY uk_event`（幂等兜底） |
| `event_type` | VARCHAR(20) | page_view / course_click / seckill_click / checkin_click | |
| `target_id` | BIGINT NULL | 目标 id（如课程 id） | 页面浏览时为 NULL |
| `device_id` | VARCHAR(64) | 设备 id | **未登录也有 id**，见讲解 ⑳ |
| `user_id` | BIGINT NULL | 用户 id | 匿名 NULL |
| `client_ts` | BIGINT NULL | 客户端时间戳（毫秒） | **BIGINT 而不是 DATETIME**，见讲解 ㉑ |
| `created_at` | DATETIME | **落库时间** | |

索引：`uk_event`、`idx_type_target(event_type, target_id)`（给热度统计）、`idx_device`（给"某设备行为轨迹"排查）。

**讲解 ⑳：为什么既有 `device_id` 又有 `user_id`**

埋点从用户打开首页那一刻就开始了，那时他还没登录（网关白名单 `/api/behavior/**` 允许匿名）。所以：
- `device_id` 由前端生成并存 localStorage，**标识"一台设备"**，永远有值；
- `user_id` 登录后才有值。
后续做「设备 → 账号」归因（同一个 device_id 后来登录了某个 user_id）就把匿名行为和实名行为串起来。这是数据仓库用户标识体系的标准起点。

**讲解 ㉑：`client_ts` 用 BIGINT 存毫秒时间戳，同时又有 `created_at`**

两个时间语义完全不同，都要留：
- `client_ts`：**事件真正发生的时间**，来自用户手机，可被篡改/时钟不准，用于分析用户行为时序；
- `created_at`：**服务端落库时间**，可信，用于对账和数据分区。
用 BIGINT 存前者：跨时区无歧义、排序方便、和前端 JS 的 `Date.now()` 直接对齐。

⚠️ 设计文档 §5 里有 `props json` 字段（存放事件的扩展属性），**SQL 和实体都没有实现**；`device_id`/`user_id` 里后者也没在消费者里填充（`BehaviorServiceImpl` 只发 deviceId 那条链路）。这块是设计与实现的偏差。

**这张表的特点：只 INSERT，永不 UPDATE。** 日志类表就该这样（append-only），所以它可以按时间分区、可以随便上冷存储。当前没做分区，数据量大了会膨胀——演示项目可接受，真实项目按天/月分表。

## 1.6 yd_community（4 张表，设计文档里它是 P1，但代码全写了）

### t_post —— 动态

| 字段 | 类型 | 含义 | 设计说明 |
|---|---|---|---|
| `id` | BIGINT AI | 主键 | |
| `user_id` | BIGINT | 作者（跨库 → yd_user） | |
| `user_name` | VARCHAR(20) | 作者昵称**快照** | 见讲解 ㉒ |
| `avatar_color` | VARCHAR(2) | 作者头像配色**快照** | |
| `content` | VARCHAR(500) | 正文 | |
| `images` | VARCHAR(100) NULL | 配图：渐变色下标 csv | 代码里 `post.setImages("")` 恒为空——图片上传是 P2 未实现 |
| `topic` | VARCHAR(20) | 话题，默认 '打卡日常' | |
| `like_count` / `comment_count` | INT | 点赞数 / 评论数 | 计数列，同讲解 ⑥ |
| `status` | TINYINT | 1 正常 0 已删除 | **逻辑删除**（软删），查列表带 `status=1` |
| `created_at` | DATETIME | | |

索引：`idx_user(user_id, status)`、`idx_time(created_at)`（Feed 拉模式按时间倒序）。

**讲解 ㉒：昵称快照 —— 微服务冗余最典型的例子**

动态列表要显示"谁发的"。用户昵称在**另一个库**（yd_user）。两种选择：

- A：每条动态实时 Feign 去用户服务查昵称 → 一次列表请求 20 条动态 = 一次批量 Feign，慢、且用户服务挂了整条 Feed 就废了；
- B：**发布那一刻把昵称复制存进 `t_post.user_name`** → 读的时候零成本。

项目选了 B（发布时 `fetchUser(userId)` 拿昵称和配色，落进动态表）。

代价：用户改昵称后，他**历史动态上的名字不会跟着变**。这在真实产品里是可接受甚至正确的（快照记录"当时是谁"，微博/知乎早期都是这么做的）。项目还额外写了 `NotifyEventConsumer`、`RankServiceImpl` 里 Feign 失败降级成"神秘运动者"，说明作者理解"远程调用一定可能失败，展示类数据要能降级"。

### t_post_like —— 点赞

`id, post_id, user_id, created_at`，**`uk_post_user(post_id, user_id)`** 唯一。

点赞是纯多对多关系，所以这张表用 `(post_id, user_id)` 复合唯一键而不是 Redis Set（设计文档里 §6 提到 `t_post_like`，实现也确实是 DB-only）。切换点赞的实现（`CommunityServiceImpl.like()`）：

```
查 (post_id,user_id) 是否已有记录
 ├ 有 → deleteById + changeLikeCount(postId, -1) → liked=false
 └ 无 → insert（DuplicateKeyException 视为重复点击，忽略）+ changeLikeCount(postId, +1) → liked=true
```

`changeLikeCount` 的 SQL 用 `GREATEST(like_count + #{delta}, 0)` —— 防并发把计数减成负数。又一个"SQL 层兜底"的小细节。

**讲解 ㉓：为什么点赞不用 Redis Set（黑马点评那种）**

黑马点评用 `SADD likes:type:id` 存点赞集合，好处是"是否点赞过"O(1)、member 计数免费。这里选了 DB：
- 因为 Feed 需要**回表拿动态详情**，反正要查 DB；
- 点赞数据不能丢，Redis 重启就没了；
- 取消点赞要的是"精确删一条"，DB 更直观。

代价是"这一页 20 条里哪些我赞过"要 `WHERE post_id IN (...) AND user_id = ?` 查一次（代码就是这么做的，`likedPostIds()`，一次查完不循环查库 —— 这点做得规范）。可以对比说明：如果量级大，就在这里加 Redis Set 做"我是否赞过"的缓存层。**能讲清两边取舍，比背八股有用得多。**

### t_comment —— 评论（两级）

`id, post_id, user_id, user_name(快照), content, parent_id, reply_to_user, status, created_at`，索引 `idx_post(post_id, status, created_at)`。

**讲解 ㉔：两级评论用 `parent_id` + `reply_to_user`，而不是无限嵌套**

`parent_id IS NULL` 是一级评论；非空是"回复某条评论"。展示时只分两层（一级列表 + 它下面的回复列表），不做无限树。

为什么不做无限嵌套：无限树要递归查询、前端渲染缩进越来越深，手机上完全不可用。微信/微博/抖音都是"两级 + 回复 @某人"。`reply_to_user` 存被回复人昵称，就为了渲染 `'回复 @张三 : 说得对'` 这一行。这是**产品形态决定表结构**的好例子。

注意 `idx_post(post_id, status, created_at)`：`status` 在中间是因为要**过滤软删**且按时间排序；等值列（post_id, status）在前、排序列（created_at）在后，索引就能同时完成过滤和排序，省掉 filesort。

### t_follow —— 关注关系（increment_2 新增）

`id, user_id(关注人), followee_id(被关注人), created_at`，索引 **`uk_follow(user_id, followee_id)`** + `idx_followee(followee_id)`。

**两个索引方向不同，服务两个不同查询**——这个必须理解：

| 查询 | 用法语 | 命中索引 |
|---|---|---|
| 我关注了谁（关注列表 / Feed 推模式的"我"侧） | `WHERE user_id=?` | `uk_follow`（最左前缀） |
| 谁关注我（粉丝列表） | `WHERE followee_id=?` | `idx_followee` |

如果只建 `uk_follow`，查粉丝就是全表扫描。**唯一键顺手当"我关注了谁"的查询索引用了**，这是省索引的常见技巧（但不要反过来把业务索引随便做成唯一键）。

### t_admin —— 管理员

`id, username, password(BCrypt), real_name, role('SUPER'/'OPERATOR'), status, created_at`，`uk_username`。

### t_operate_log —— 操作日志

| 字段 | 含义 |
|---|---|
| `admin_id` / `admin_name` | 操作人（**冗余快照**，管理员改名/删号后日志仍可读） |
| `module` / `operation` | 业务模块 / 操作描述 |
| `method` | 请求方法（类名+方法名） |
| `params` | 参数 JSON（`VARCHAR(500)` 截断存，防爆） |
| `ip` | 操作 IP |
| `duration_ms` | 耗时（毫秒） |
| `success` | 是否成功 |

由 `OperateLogAspect`（AOP 切面）自动写，全项目**唯一的 @Aspect**。

⚠️ **这里有个确定的 bug**：切面把写日志丢进独立线程池（`operate-log` executor）异步执行，而 `AdminContext` 是普通 `ThreadLocal` —— 换线程后读不到，`adminId`/`adminName` 恒为空，所以**每条日志的操作人都是 `0` / `'未知'`**（表字段 NOT NULL，代码塞了默认值）。这个必须改（第三部分 P0-6）。

**RBAC（Role-Based Access Control，基于角色的权限控制）**：
- 角色存在 `t_admin.role`，只有两个值；
- 管理端服务里用 `@RequireRole("SUPER")` 注解 + `AdminAuthInterceptor` 拦截器校验（方法上的注解优先于类上的注解，`SUPER` 无条件放行）；
- 角色在**登录时写进 JWT 的 `role` claim**，之后每次请求从 token 里读；
- 菜单：`AuthAdminController.ROLE_MENUS` 硬编码两个角色各能看哪些菜单。

⚠️ 由此带来一个安全性问题：token 有效期 720 分钟（12 小时），**把角色塞进 token 就意味着降级/禁用一个管理员后，他手里的旧 token 在整个有效期内仍然有效**。真实做法是版本号/黑名单，或每次请求回查 DB。见第三部分 P1-8。

## 1.9 第二数据库：Redis 结构（很多状态根本不在 MySQL）

这个项目有相当一部分业务状态**只存在 Redis**，理解这一点才能理解流程。Key 常量集中在 `fitness-common/.../constant/RedisKeyConstants.java`：

| Key | 类型 | 存什么 | 丢了会怎样 |
|---|---|---|---|
| `seckill:stock:{activityId}` | String | 秒杀剩余库存 | 活动期无法抢购（可由定时任务从 `remain` 重新预热） |
| `seckill:bought:{activityId}` | Set | 已抢到的用户 id | **一人一单失效，同一人能再抢** |
| `seckill:result:{seqId}` | String(10min) | QUEUEING / SUCCESS:订单号 / FAIL:原因 | 前端轮询到"排队超时" |
| `course:detail:{id}` | String(JSON) | 课程详情 + 内嵌逻辑过期时间 | 回源查库，无业务损失 |
| `course:empty:detail:{id}` | String(2min) | 空值标记（防穿透） | 无 |
| `course:lock:…`（实际复用详情 key） | Redisson String | 缓存重建互斥锁 | 无 |
| `store:geo` | GEO | 门店经纬度 | 启动时 `ApplicationRunner` 自动重建 |
| `point:check:{yyyyMM}:{userId}` | Bitmap | 当月哪几天打了卡 | **打卡明细全丢，连续天数无法重建** ← 最严重 |
| `rank:month:{yyyyMM}` | ZSet | 月度积分榜（member=userId） | 榜单空，可从流水重算 |
| `feed:inbox:{userId}` | ZSet(留最近1000) | 关注流收件箱（score=发布时间） | 关注流变空（可改拉模式或重建） |
| `behavior:hot:course:{yyyyMM}` | ZSet(40天) | 课程点击热度 | 首页推荐退化为默认顺序 |
| `coupon:stock:{id}` / `coupon:got:{id}` | String / Set | 券库存 / 领取资格 | 同秒杀 |
| `idempotent:msg:{msgId}` | String(24h) | MQ 消费幂等 | 有 DB 唯一索引兜底 |
| `admin:captcha:{id}` | String(2min) | 图形验证码答案 | 重新生成即可 |

**为什么要知道这张表**：面试问"你 Redis 和 MySQL 怎么保持一致"，能具体说出「哪些数据只在 Redis、丢了怎么恢复、哪些有 DB 兜底」才是真懂。这个项目里 **Bitmap 打卡是唯一"真相只在 Redis"的数据**，是明显的短板（第三部分 P0-5）。

## 2.1 一次请求的完整通路（所有功能共用的骨架）

```
浏览器 → vite dev proxy (/api → :8080) 或 Nginx
  ↓
fitness-gateway  :8080
  AuthGlobalFilter (order=-100)
    1) path 含 "/inner/"        → 直接拒（内部接口不允许外部触达）
    2) 命中 auth.whitelist 前缀  → 放行，并**移除** X-User-Id（防伪造）
    3) 取 Authorization，必须 "Bearer " 前缀，substring(7)
    4) JwtUtil.parseUserId(token) → 失败一律 TOKEN_INVALID
    5) 成功 → 覆盖写入 X-User-Id 请求头，转发
  ↓ 路由：StripPrefix=1，即 /api/course/list → 转发 /course/list
业务服务 :81xx
  UserContextInterceptor (common 里，注册到所有 servlet 应用)
    读 X-User-Id → UserContext ThreadLocal；afterCompletion 里 clear
  Controller：userId 一律 UserContext.get()，**从不接受前端传 userId**（防越权）
  Service → Mapper(MyBatis-Plus) / Redis / RabbitTemplate
  返回 Result{code,message,data}；异常由 GlobalExceptionHandler 统一转 Result
  ↓
Feign 内部调用时：FeignUserRelayInterceptor 把 ThreadLocal 的 userId 和原始
Authorization 抄到下游请求头，链路不断
```

这一层的意义：`userId` 从网关注入、拦截器落到 ThreadLocal、Service 只从上下文取 —— **业务代码里不存在"前端说我是谁"这回事**。项目实现得挺干净，`markRead` 这类更新语句也都带 `userId` 条件（防 IDOR 越权）。

但注意两个实现瑕疵（第三部分 P0-1、P0-2）：网关白名单用 `String::startsWith` 而不是路径匹配器，导致 yml 里 `"/api/admin/**"` 和 `"/**/v3/api-docs"` **永远不匹配**（它们带 `*` 是 glob 语法，不是前缀）；拒绝响应的 HTTP 状态码**恒为 401**，403 场景也返回 401。

## 2.3 核心链路的代码流程（逐条讲清"为什么这么走"）

### 链路 A · 课程详情缓存（`CourseServiceImpl.getDetail()`，L98-149）

```
1 redis.GET course:detail:{id}
  命中 ─┬─ 逻辑未过期(wrapper.expireTime > now) → 直接返回          ← 绝大多数请求，零 DB
        └─ 逻辑已过期 →
             redisson.getLock(course:detail:{id}).tryLock()
              ├─ 抢到 → 双重检查（可能已被前一个持锁线程重建完）
              │        → 还没重建则 rebuildExecutor.submit(重建)  ← 异步，本请求不等
              │        → finally unlock
              └─ 没抢到 → 直接返回**旧数据**          ← 这就是"防击穿"
             返回旧数据
  未命中 →
2 redis.HASKEY course:empty:detail:{id} ? 是 → 抛 COURSE_NOT_FOUND   ← "防穿透"（空值缓存）
3 selectById → null 则 SET 空值标记 TTL 2min 后抛异常
4 writeCache(vo) → 返回
```

**逻辑过期 vs 物理 TTL 的区别（这是这段代码的核心思想，务必吃透）**：

- 物理 TTL：Redis 自己记的过期时间。到点 key **消失**，下一个请求必然打到 DB。
- 逻辑过期：key **物理上永不过期**，把"业务上的过期时间"当成 JSON 里的一个字段（`CacheWrapper.expireTime`）存进去。读到数据发现逻辑上过期了，就**先把旧数据返回给用户 + 后台线程去重建**。

好处是**没有请求会因重建而等待**（读写都不阻塞），这就是"逻辑过期"方案相比"互斥锁阻塞重建"的优势：黑马点评里用的是互斥锁 + 阻塞重建（第一个线程重建，其他人循环重试读缓存），本项目用的是逻辑过期 + 异步重建（没人阻塞）。

⚠️ 但设计文档承诺的"缓存三件套"里，**第三件（防雪崩）只做了一半**：`writeCache` 调的是**不带 TTL 的两参数 set**，即 Redis 层面这些 key **永不过期**。那个 `BASE_TTL(30min) + ThreadLocalRandom 0~5min` 只是拿来算逻辑过期时间戳的。结果：Redis 里课程详情 key 只增不减，重启后全部回源。这个我列在 P1-2 建议里。

其他细节：锁的 key **复用了数据 key**（`RedisKeyConstants.COURSE_LOCK` 定义了但没被用），`tryLock()` 没传 leaseTime（持锁线程崩溃靠 Redisson 看门狗，但如果只是慢就会一直占锁）——这两点也在建议里。

### 链路 B · 普通预约下单（`BookingServiceImpl.create()`，L61-158）

```
① Feign 查课程简况（courseClient.detail）→ 不存在直接报错
② Feign 查场次（courseClient.schedule）→ 不存在/已取消报错
③ 校验 schedule.courseId == 请求的 courseId     ← 防"张冠李戴"传错场次 id
④ 如果带了券：couponClient.info(recordId,userId,原价) → isUsable? 不通过则抛具体原因
   finalPrice = 原价 - discount（max 0）
⑤ 同人同课去重：COUNT(user_id, course_id, status IN UNPAID/BOOKED) > 0 → BOOKING_DUPLICATE
   （命中 idx_course_user 索引）
⑥ 满员预检：schedule.booked >= capacity → COURSE_FULL   ← 只是"预检"，不是最终防线
⑦ Feign 原子占位：courseClient occupySchedule(scheduleId)
   → 内部执行 UPDATE ... WHERE id=? AND booked<capacity AND status=1，看影响行数
   影响 0 行 → COURSE_FULL，一个名额都没占，直接返回
⑧ 建单 insert（status=UNPAID, order_no, schedule_id, coupon_record_id, discount_amount）
   insert 抛异常 → 补偿：releaseSchedule() 释放刚占的名额，再抛系统错误
⑨ 核销券：couponClient.use(recordId, userId, orderNo)  ← UNUSED→USED 的 CAS + 绑订单号
   失败 → releaseSchedule 回滚名额 → 抛"优惠券核销失败"
⑩ 发 15 分钟延迟取消消息 + 发站内通知 → 返回订单 VO
```

**几个值得学的点**：

- 顺序是"**先占资源，再落自己的单，失败就补偿**"。这是跨服务事务的唯一现实做法（没有 Seata），叫 **TCC 风格的补偿**（Try-Confirm-Cancel）。代码在⑦⑧⑨三处都写了释放补偿。
- 补偿链是**手工编排**的，所以有漏洞：⑨ 里核销券失败时释放了名额，但**⑧ insert 成功、⑩ 发送 MQ 失败** 这种分支就没有补偿了（消息丢了 → 订单永远停在 UNPAID，靠用户手动取消）。
- 真正的防超约在第⑦步的那条 UPDATE，第⑥步只是让大多数情况少一次 RPC。理解「预检 vs 原子判定」的分工很重要。

**⚠️ 这条链路上最大的设计缺失**：第⑤步的"同人同课去重"是先查再插，**没有唯一索引兜底**（`idx_course_user` 是普通索引）。两个并发请求可以同时通过⑤，然后各占一个名额、各建一单 → 同一个人同一门课两张有效单。按项目其他地方一贯的水准，这里本该加一个**函数式唯一索引**或 Redis SETNX。列入 P1-1。

### 链路 C · 模拟支付与核销码生成（`BookingServiceImpl.pay()`，L172+）

```
UPDATE t_booking SET status='BOOKED', pay_time=NOW()
 WHERE order_no=? AND user_id=? AND status='UNPAID'          ← CAS
影响 0 行 → BOOKING_STATUS_ERROR（已支付/已取消，重复支付天然失败）
然后生成核销码：SecureRandom 取 10 位数字，insert/update 遇 DuplicateKeyException 重试 3 次
发站内通知
```

- 支付"成功"是假的（没有接微信支付），但**状态流转的写法是真的**：一条 CAS UPDATE 同时完成校验和变更，`status='UNPAID'` 这个条件保证了「已取消的单不可能被支付」，这是延迟取消链路能安全工作的基础。
- 核销码用 `SecureRandom`（密码学安全随机）而不是 `Random`，且靠 `uk_verify_code` + 重试防碰撞 —— 但**第 3 次还撞上就只记日志继续走**，导致 `verify_code` 留 NULL，用户没码不能核销。概率极低但处理不对（P2）。

核销（`verifyByCode`，L235-253）：

```
按码查订单（展示 + 预判状态）
UPDATE ... SET verified_at=NOW(), status='FINISHED' WHERE verify_code=? AND status='BOOKED'  ← CAS
影响 0 行 → "该核销码已使用或订单状态不允许核销"
发通知
```

重复核销被 CAS 拦住 —— 又是同一招。调用方是 `fitness-admin-server` 的 `VerifyAdminController`（**它漏了 `@RequireRole`**，见 P0-4）→ Feign `BookingClient` → `InnerBookingController /inner/booking/verify`。

### 链路 D · 秒杀：Lua + MQ 异步建单 + 轮询（`SeckillServiceImpl.book()`，L58-111）

```
同步部分（接口只做两件事：一条 Lua + 一条 MQ）
① Feign courseClient.activeSeckill(courseId) → 取进行中的活动
   不存在 → SECKILL_NOT_ACTIVE
② seqId = UUID.randomUUID()
   SET seckill:result:{seqId} = 'QUEUEING' TTL 10min   ← 先写，保证前端第一拍就轮询得到
③ ttlSeconds = max(60, (active.endTime - now)/1000)
   redis.execute(lua/seckill.lua,
       keys = [seckill:stock:{actId}, seckill:bought:{actId}],
       args = [userId, ttlSeconds])
     返回 1 → SET result='FAIL:已抢完' + 抛 SECKILL_SOLD_OUT
     返回 2 → SET result='FAIL:已抢过' + 抛 SECKILL_DUPLICATE
     返回 0 → 库存已扣、资格已记录，继续
④ 发 MQ 到 ex.order.seckill / routingKey=seckill.create，
   body = {msgId=UUID, seqId, userId, activityId, courseId}，AMQP messageId = msgId
   ⚠️ 发送抛异常 → 手动回补：INCR 库存 + SREM 资格集合 + 写 FAIL 结果 + 抛系统错误
⑤ 立刻返回 {seqId}     ← 全程没碰 MySQL

异步建单（SeckillCreateConsumer）
① SETNX idempotent:msg:{msgId} 24h；已存在 → 直接 ack（重复投递）
② courseClient.deductRemain(activityId)   ← DB 的 remain -1（账本落账）
③ Feign 查课程/活动信息 → insert 订单（status=UNPAID, activity_id 非空, price=秒杀价）
④ 发 15 分钟延迟取消消息
⑤ SET seckill:result:{seqId} = 'SUCCESS:'+orderNo
⑥ basicAck
   业务异常 → restoreStock（INCR + SREM）+ SET result=FAIL + ack（不再重试）
   未知异常 → restoreStock + SET result=FAIL + basicNack(requeue=false) → 进 DLQ q.order.seckill.dlq
   JSON 解析失败 → nack 进 DLQ

轮询 GET /seckill/result?seqId → 读 Redis，按前缀解析
   'SUCCESS:xxx' → {status:SUCCESS, orderNo:xxx}
   'FAIL:原因'   → {status:FAIL, reason}
   其它          → {status:QUEUEING}
   key 不存在     → {status:FAIL, '排队超时，请重试'}   ← 前端最多轮 20 次(10s)，key 有 10min 所以不会真超时
```

**Lua 全文**（`fitness-order/src/main/resources/lua/seckill.lua`）：

```lua
if tonumber(redis.call('GET', KEYS[1]) or '0') <= 0 then
    return 1
end
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return 2
end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
-- 资格集合跟随活动结束时间过期，活动结束后自动清理
redis.call('EXPIRE', KEYS[2], tonumber(ARGV[2]))
return 0
```

`or '0'` 很关键：库存 key 不存在（没预热/已过期）时 `GET` 返回 `false`，`tonumber(false)` 是 nil，加 `or '0'` 兜成 0 → 判为"抢完"。**宁可不卖也不超卖**，这个默认值方向是对的。

**为什么"异步排队 + 轮询"而不是同步下单**：秒杀的峰值 QPS 可能是平时的 100 倍，DB 写一秒钟只能扛几百。同步做就要么拒绝用户要么数据库崩。改成"Redis 判定资格 + 消息排队 + DB 匀速消费"，DB 压力从尖峰变成平缓曲线，用户只多等几百毫秒。**这是削峰填谷最标准的形态**，也是本项目最值得讲的一条链路。

⚠️ 这条链路缺了设计文档承诺的两样东西：**`@RateLimit`（限流）和 `@Idempotent`（接口防重）在代码里根本不存在**（我全仓 grep 过，0 命中，连注解类都没有）。后果：
- 没限流 → 任何人都能拿脚本无限打 `/api/seckill/book`，网关和 order 服务裸奔；Redis 会被打死。
- 没接口防重 → 同一次点击的重传/双击，虽然 Lua 里的 SISMEMBER 会拦下第二次的**资格**，但第一次已进队列、第二次抛异常，前端表现为"已抢过"——勉强能自圆。真正的风险在**普通预约接口 `/booking/create` 完全没有任何防重**，双击就是两次下单请求（第⑤步的去重不是原子，于是有了链路 B 那个并发重复下单的洞）。

这两个注解必须补，是 P0-9。

### 链路 E · 15 分钟未支付自动取消（`sendTimeoutMessage` + `BookingTimeoutConsumer`）

```
生产：convertAndSend(ex.order.delay, 'order.timeout', {orderNo,userId},
                     m -> m.setDelay(15*60*1000))     ← x-delay 头 = 900000ms
交换机类型：CustomExchange('ex.order.delay','x-delayed-message', durable, {x-delayed-type:direct})
           （需要 RabbitMQ 的 x-delayed-message 插件，镜像用 lifetools-rabbitmq:3.13-delayed）

消费：按 orderNo 查订单
      status != UNPAID → 直接 ack 放过（已支付/已取消，什么都不做）  ← 这是"撤回延迟消息"的替代方案
      CAS UPDATE ... SET status='CANCELED' WHERE order_no=? AND status IN ('UNPAID','BOOKED')
      rows>0 才释放名额（releaseSchedule / release）+ 退券 + 通知
      异常 → basicNack(requeue=**true**)
```

**"延迟消息如何取消"这个经典问题的答案**：设计文档里就写明了 —— **不撤回，靠消费时的状态校验来幂等**。因为 RabbitMQ 的延迟消息投出去就收不回。消费时先看状态，已支付就 ack 丢弃。这是很实用的思路，面试讲这个比讲"怎么实现撤回"更有说服力。

⚠️ 但**失败重投用了 `requeue=true`**：如果某条消息处理一直抛异常（比如课程服务挂了），它会**无限立即重投**，把消费者线程打满 —— 这就是代码注释自己都承认的"毒消息"（poison message）问题。`q.order.timeout` **也没挂 DLX**。这两点必须改（P0-10）。

### 链路 F · 完课 → 加 30 积分（跨服务事件，`VideoServiceImpl` → `CourseEventPublisher` → `CourseFinishedConsumer`）

```
course: POST /video/progress {videoId, progress}
  ① 取 t_video_progress 现有行（uk_user_video 保证一人一视频一行）
  ② 防刷：elapsed=(now-last_report_at)，要求 progress 增量 ≤ elapsed*1.5 + 15，否则拒绝
  ③ finishedNow = (newProgress>=100 && !alreadyFinished)
  ④ advance（UPDATE ... WHERE progress < newProgress）；无行则 insert（DuplicateKey 忽略）
  ⑤ finishedNow → rabbitTemplate.convertAndSend(ex.course.event,'course.finished',
        {eventId=UUID.randomUUID(), userId, videoId, points:30})
        ⚠️ 发送失败只 log.warn，不抛（"演示项目从简"）

point: 监听 q.point.course.finished（绑定 ex.course.event / course.finished）
  ① SETNX idempotent:msg:{eventId} 24h → 已存在直接 ack
  ② addEventPoints(userId, 30) + insert PointsLog(COURSE_FINISHED, biz_id=eventId)
     DuplicateKeyException（uk_biz 唯一索引）→ 视为已处理，ack
  ③ ZINCRBY rank:month:{yyyyMM} +30
  ④ 发"完课奖励"站内通知
```

**⚠️ 这条链路上有一个会导致重复加分的确定 bug**（P0-3）：

`t_video_progress.finished` 这一列，**代码里从来没把它置成 1**。`advance` 那条 UPDATE 只更新 `progress`（和 `last_report_at`），`finished=1` 只存在于首次 insert 的分支里。所以用户看完一次（100%）之后，`alreadyFinished` 从 DB 读回来永远是 `false`，之后**每次上报 100% 都判定为"本次刚完课"**，每次都发一个事件、而且每次 `eventId` 是**新 UUID**。

于是两层幂等全部失效：Redis 用 eventId 去重（每次不同），DB 用 `(COURSE_FINISHED, eventId)` 唯一索引（每次不同）。结果：用户在视频页反复拖动/暂停，就可能反复 +30，排行榜也跟着涨。**这是我建议优先修的第一个真 bug**，修法很小：`advance` 里加 `finished = IF(#{newProgress}>=100,1,finished)`。

### 链路 G · 每日打卡（Bitmap + ZSet，`CheckinServiceImpl.doCheckin()`）

```
key = point:check:{yyyyMM}:{userId}，offset = 当月第几天 - 1（1号→0）
① GETBIT key offset → 1 则 CHECKIN_DUPLICATE
② SETBIT key offset 1
③ BITFIELD 一次取出「1号..今天」共 dayOfMonth 个 bit → 从最低位往高数连续 1 的个数
④ 记账：selectById 账户不存在则 insert(首卡)，DuplicateKey → 转 addCheckinPoints（并发首卡兜底）
⑤ insert PointsLog(CHECKIN, biz_id=当天日期串)
⑥ ZINCRBY rank:month:{yyyyMM} userId +10
⑦ 发站内通知
⑧ 回读最新余额 → 返回 {本次加分, 连续天数, 余额}
```

**讲解：BITFIELD 怎么算连续打卡天数**（`countContinuous()`，L174-186）

Bitmap 里第 0 位是 1 号、第 1 位是 2 号……`BITFIELD key GET u15 0` 就是"从第 0 位开始读 15 个 bit，当成一个无符号整数返回"。假设今天是 13 号，读了 13 位，那么这个整数的**最低位（bit 0）对应 1 号，第 12 位对应 13 号（今天）**。

连续打卡要求"今天、昨天、前天……一直往前是 1"，但位的编号是日期递增的，所以连续段是**从高位往低位数**还是**从低位数**？代码是这么写的：

```java
while (((bits >> continuous) & 1) == 1 && continuous < dayOfMonth) { continuous++; }
```

`bits >> 0 & 1` 是 **1 号**那位。也就是说它数的是"从 1 号开始的连续 1 的个数"，而不是"从今天往回数的连续值"。

于是 `continuous_days` 的真实语义是 **"本月从 1 号起连续打卡的天数"**。如果用户 3 号才开始打，1 号位是 0，连续天数算出来就是 **0**（哪怕他连打了 10 天）。

这是个**语义 bug**（P1-4）。正确写法应该是从今天（第 `dayOfMonth-1` 位）往低位数：

```
for (int i = dayOfMonth - 1; i >= 0; i--) { if ((bits >> i & 1) == 1) continuous++; else break; }
```

（跨月的连续性它也没考虑 —— 严格来说"连续天数"要能跨月，那就得读上月位图，或者干脆把 Bitmap key 改成"以天为单位的偏移"（如 `point:check:{userId}` + offset = 距 epoch 的天数，这是更常见的做法，也天然支持跨月和"任意区间统计"）。这是我很建议改的一处，因为它同时解决语义 bug 和"Redis 丢了无法重建"。）

另外两条：
- **GETBIT 判重 + SETBIT 不是原子**（应该 Lua 一句 `if GETBIT==0 then SETBIT`）→ 并发双击**双加分双 ZINCRBY**（P1-7）。
- **`doCheckin` 没有 `@Transactional`**，而 SETBIT 在 DB 写之前 → DB 挂了但位已置，用户当天再也打不了卡，积分白丢（P1-7）。

**讲解：排行榜为什么用 ZSet + 为什么现在榜是错的**

`rank:month:{yyyyMM}`，member = userId，score = 本月积分。`ZINCRBY` O(log N) 加分、`ZREVRANGE 0 49 WITHSCORES` 取 Top50、`ZREVRANK` 查我第几名 —— 三个命令就把"月度积分榜"全包了，DB 一行都不用扫。设计没问题。

⚠️ 问题是**只有打卡路径 ZINCRBY 了**：完课 +30（`CourseFinishedConsumer`）加了 DB 余额但**没写 ZINCRBY**，兑换扣分也没减。于是榜单和 `balance` 会静默背离，且没有任何修正机制。这是 P0-6 级的问题（它让"排行榜"这个亮点站不住）。

`RankServiceImpl` 的其余逻辑：取 Top50 → 收集 userId → **一次** `userClient.batch()` 补昵称（失败则昵称降级为"神秘运动者"）→ 我不在 Top50 时额外 `ZREVRANK` + `ZSCORE` 把我这行拼到末尾（昵称写死 `'我'`）。⚠️ 没有分页参数（`TOP_N=50` 硬编码），⚠️ 榜空时抛"榜单暂时为空"而不是返回空列表（前端首屏会红字报错）。

### 链路 H · 埋点闭环：前端 → Kafka → 落库 → 热度榜 → 首页推荐

这是项目里唯一用 **Kafka** 的链路，也是它和设计文档"双 MQ"说法的落点。

```
前端（fitness-web/src/utils/track.js）
  installTrackRouter(router) → router.afterEach 自动 track('page_view')
  手动埋点：checkin_click / seckill_click（course_click 在课程列表页漏了 ← 关键缺陷）
  本地攒批：满 5 条 或 3 秒定时器 → POST /behavior/report {deviceId, events:[...]}
  beforeunload 时强制 flush（用普通 XHR，尾部事件可能丢）

behavior 服务
  POST /behavior/report → @Valid ReportDTO（deviceId 非空、events 非空、每条 eventId 非空、
                          event_type 必须 @Pattern 匹配那 4 种）
  逐条 kafkaTemplate.send('yd-behavior-event', deviceId, json)   ← key=deviceId
  立即返回 Result.ok()（设计文档说要 202，实现是 200）

  @KafkaListener(topic='yd-behavior-event', groupId='yd-behavior-consumer')
    ① SETNX behavior:seen:{eventId} 24h → 重复则 return
    ② insert t_behavior_log（uk_event 唯一索引兜底）
    ③ event_type=='course_click' && targetId!=null
       → ZINCRBY behavior:hot:course:{yyyyMM} targetId +1，并 EXPIRE 40 天

  GET /behavior/hot/courses?limit=3 → ZREVRANGE 0..limit-1 WITHSCORES → [{courseId, clicks}]

前端首页 HomePage：拉 hot/courses → 按点击热度**重排推荐课程**
```

**为什么埋点用 Kafka 而不用 RabbitMQ**（这个理由要能自己讲出来）：
- Kafka 是**分区日志**（partitioned log）模型，顺序追加写磁盘吞吐极高，天然适合"只写不改"的事件流；
- Kafka 可以**按 key 保序**：`key=deviceId` → 同一设备的事件必然进同一分区 → 消费时同设备顺序不乱（同一用户"先进详情页→再点击"这类序列不会颠倒）。这是 RabbitMQ 做不好的（Rabbit 只在单队列单消费者下保序，一开并发就乱）；
- Kafka 消息可**回溯重放**（offset 能倒回去）—— 埋点算错了改个消费逻辑重跑就行，Rabbit 消费即销毁。
- RabbitMQ 则胜在路由灵活、有延迟消息插件、有 DLX、有确认机制，所以**业务指令**（建单、延迟取消、积分事件）走 Rabbit。

⚠️ 这条链路当前有 3 处会削弱"Kafka 高保序/可靠"的说法（P1-9）：
1. **消费者用的是默认 auto-commit**，没设 `ack-mode`，与设计文档 §7 的"消费者手动 ack"矛盾；一旦 `insert` 抛异常被外层 catch 吞掉，offset 照样前进 → **消息静默丢失**。
2. `application.yml` 把 `key-serializer`/`value-serializer` 写在了 **consumer** 节点下（应该是 `key-deserializer`/`value-deserializer`）—— Spring Boot 会忽略这两个未知属性，虽然因为默认反序列化器刚好能用而"没出事"，但这是明显的低级错误。
3. **topic 从来没被显式创建**：全项目没有 `NewTopic` Bean，靠 `KAFKA_AUTO_CREATE_TOPICS_ENABLE=true` 自动建，而自动建用的是 broker 默认分区数（**1 个分区**）。所以"3 分区、同设备有序"这个说法在真实环境里目前只能落到 1 分区上（1 分区也保序，但吞吐是单点）。
4. `ReportDTO.events` 上的 `@Size(max=20)` 没写（注释里说有），一次可以传任意多条 → 埋点接口变成 DDOS 放大器；`props` 字段整条链路都丢了。

### 链路 I · Feed 推模式收件箱（`CommunityServiceImpl.publish()` / `followFeed()`）

```
写（推）：
  Feign 拿作者昵称/配色 → insert t_post
  followerIds = followService.followerIds(作者id)      ← SELECT followee_id FROM t_follow（无 LIMIT）
  for each fid:
     ZADD feed:inbox:{fid} score=now postId
     ZREMRANGEBYRANK feed:inbox:{fid} 0 -1001           ← 收件箱只留最近 1000 条

读：
  tab=='all'    → DB 按 created_at 倒序分页（拉/普通查询）
  tab=='follow' → ZREVRANGE feed:inbox:{me} start..start+19 → 得到 postId 列表
                  → selectList(WHERE id IN (...)) 一次回表（不循环查库）
                  → 过滤 status==1 → 按 ZSet 返回的顺序组装
                  → ZCARD 判断 hasMore
```

**讲解：推模式（写扩散）vs 拉模式（读扩散）—— 这个项目取了推，但只做了"教科书版"**

- **推（写扩散）**：发动态时就把 id 写进每个粉丝的收件箱。读的时候 O(1) 直接读自己的 ZSet，**读极快、分页天然稳定**（score 就是时间戳）。代价是**写放大**：10 万粉丝就是 2 万次 Redis 写。
- **拉（读扩散）**：只存自己的动态。读时把"我关注的所有人"的最新动态捞出来归并排序。写便宜，读昂贵，翻页容易错位。
- **推拉结合**（真实做法）：普通用户推，大 V 不推（粉丝读时再拉大 V 的动态归并进去）。代码注释里就写了这句（"大 V 百万粉丝场景应改推拉结合"），**但没实现**。

当前的实现问题（P1-10）：扇出**完全在请求线程里同步做**，`followerIds()` 无上限，每个粉丝**两次串行 Redis 往返**（ZADD + ZREMRANGEBYRANK）。1000 个粉丝 = 2000 次串行网络往返，发动态接口直接变成几秒。至少应该：pipeline 批量、去掉每次的 trim（改成写满阈值再 trim）、或者异步（丢线程池/MQ）。

⚠️ 还有 `commonFollow()`（共同关注）用 `SINTER community:following:{a} community:following:{b}`，而这个 Set **只在 follow() 时写**、`isFollowing` 走的是 DB —— 于是 Redis 一旦清空，共同关注永远是空。代码注释承认"简化"，但这是"缓存既当缓存又当唯一数据源"的典型反模式（P2）。

### 链路 J · 管理端 BFF（Backend For Frontend，为前端专门包一层的后端）

```
fitness-admin (Element Plus, :5174)
  → vite proxy /api → gateway :8080
  → 网关路由 /api/admin/** → lb://fitness-admin-server (8107), StripPrefix=1
  → AdminAuthInterceptor：放行 /admin/auth/captcha|login，其余校验管理端 JWT
       + @RequireRole("SUPER") 方法/类注解校验（SUPER 无条件通过）
  → Controller：绝大多数是**一行 Feign 透传**
       CourseAdminController → CourseAdminClient → fitness-course /inner/course/admin/**
       GiftAdminController   → PointClient        → fitness-point /inner/point/gift/**
       OrderAdminController  → BookingClient      → fitness-order /inner/booking/admin/**
       MemberAdminController → UserClient         → fitness-user /inner/user/admin/**
       VerifyAdminController → BookingClient      → /inner/booking/verify
  → 只有两处做真正的"聚合"：
       OrderAdminController：订单分页 + Feign 批量补用户昵称
       MemberAdminController：用户分页 + pointClient.brief() 补积分
  → OperateLogAspect 异步落 t_operate_log
```

**讲解：这里的 BFF 是"薄透传 + 少量聚合"**

33 个类里没有复制任何业务逻辑，管理端所有写操作都回到各个业务服务的 `/inner/**`。这是**正确**的 BFF 形态（业务规则的唯一定义点在业务服务里，管理端只负责"组装视图 + 权限 + 审计"）。真正聚合的只有两个列表补昵称/补积分。

`/inner/**` 的约定也落实了：网关对含 `/inner/` 的路径直接拒绝，所以外部无法绕过管理端鉴权直连内部接口。这个设计很干净，值得肯定。

⚠️ **但管理端目前端到端跑不通**，原因分两类：

1. 网关白名单 `startsWith` 那个 bug 让 `/api/admin/**` **需要用户侧 JWT**，而管理员登录时还没有任何 token → 登录接口自己就 401，整个后台进不去（P0-1，一行代码可修）。
2. 前端 `src/api/index.js` 声明的 29 个路径里，**9 个路径与后端不一致、11 个请求体形状不对、3 个响应结构不对**：
   - 前端 `/admin/course/list` ↔ 后端 `GET /admin/course/page`；`/admin/member/list` ↔ `/page`；`/admin/order/list` ↔ `/page`；`/admin/schedule/*` ↔ `/admin/course/schedule/*`；`/admin/verify/code` ↔ `/admin/verify/do`；`/admin/verify/logs` ↔ `/admin/verify/recent`；`/admin/dashboard/summary` ↔ **后端根本没有 dashboard 控制器**；
   - 后端一堆 `@RequestParam` 的 POST（改状态、删课程、结束秒杀、核销、加库存），前端**一律 `post(url, JSON)`**，从不发 query 参数或表单 → 全 400/415；
   - 后端 `/admin/seckill/list`、`/admin/store/list`、`/admin/course/schedule/list` 返回**裸 List**，前端按 `data.list` 读 → 空表。
   
   根因很实在：**Mock 的 handler 用 `url.startsWith(前缀)` 匹配，所以前端自己造的路径在 Mock 下"永远能用"，从来没有人核对过真实 Controller 上的注解**。这就是长期 Mock 不联调的必然结局（P0-11）。

## 2.5 可靠性机制的实际情况（对照设计文档 §7）

| 设计文档承诺 | 代码实际 |
|---|---|
| 生产者 publisher-confirm + 失败落日志表 | `publisher-returns:true` 配了，但**没有 ReturnsCallback、没设 mandatory**；`ConfirmCallback` 那个 Bean 写成了 `@Bean RabbitTemplate confirmCallback(RabbitTemplate…)` —— 自注入循环，很可能启动即失败，而且就算成功也是把回调设在无人使用的实例上。完课事件发送失败只 `log.warn`。 |

| 异常 nack 重试 1 次后进死信 | 秒杀 ✅（requeue=false 直接进 DLQ）；超时取消 ❌（requeue=**true** → 无限重投） |

| JWT 签发/校验、上下文透传、`/inner` 不外泄 | ✅ 全部实现，且 `X-User-Id` 覆盖写入防伪造，Feign 透传拦截器齐备 —— 这块是做得最好的 |
| 空值缓存 / 逻辑过期 / 互斥重建 | ✅ 前两个实现了；❌ 物理 TTL/随机过期（防雪崩）没做 |
| 布隆过滤器 | ❌ 没有（全仓 grep 无 Bloom）——但有空值缓存，穿透防护其实够用 |

| `t_course.store_id` / `store_name` | 一门课只属一家店 | **升级为多对多** `t_course_store` |
| `t_course.coach` / `coach_title` | 没有教练实体 | **删**。由 `t_coach` + `t_coach_course` 取代 |
| `t_booking.book_time`（字符串文案） | 订单绑死一个时刻 | **删**。订单不再有时间，时间在 `t_reservation` |
| `t_booking.schedule_id` | 约的是场次 | **删** |
| `t_booking` 兼任"预约单" | 下单即预约 | **拆表**：`t_booking` = 购买流水，预约 = `t_reservation` |

**顺带消解的第三部分问题**：P1-3（秒杀单时间是"预约制"文案、不占场次容量）——秒杀卖的是权益，本就不该有上课时间；`total=30` 的语义变成"能卖 30 份权益"，与教练有几小时空闲完全解耦。**P1-8 / P0-2**（token 不可撤销、403 返 401）由 4.6/4.7 修。

### 4.1.2 三条状态机轴（**整套设计里最重要的结构决定**）

| 轴 | 表 | 状态流转 | 谁推进 |
|---|---|---|---|
| **订单（钱）** | `t_booking` | `UNPAID → PAID`；`UNPAID → CANCELED`；`PAID → REFUNDED` | 用户支付 / 15 分钟超时 / 主动取消 / 过期退款任务 |
| **凭证（权益）** | `t_entitlement` | `ACTIVE → USED_UP`（按次用完）；`ACTIVE → EXPIRED`（过期） | 到点扣次 / 过期任务 |
| **预约（时段）** | `t_reservation` | `BOOKED → FINISHED`（上完）；`BOOKED → CANCELED`（用户取消） | 到点任务 / 用户取消 |

**"已过期"不是订单状态，"待使用"不是预约状态。** 这三个字段分属三张表，谁也别往谁身上套。

第 9 条"我的页面 tab" → 查询映射：

| tab | 数据来源 | 查询 |
|---|---|---|
| 待支付 | 订单轴 | `t_booking WHERE user_id=? AND status='UNPAID'` |
| 待使用 | 凭证轴 | `t_entitlement WHERE user_id=? AND status='ACTIVE' AND (total_times IS NULL OR used_times < total_times)` |
| 已预约（即将上课） | 预约轴 | `t_reservation WHERE user_id=? AND status='BOOKED' AND start_time > NOW()` |
| 待评价 | 订单轴 + 评价表 | `t_booking WHERE status='PAID'` 且 `t_rating` 无该 `order_no`（LEFT JOIN 判空） |
| 已完成 | 订单轴 | `status='PAID'` 且凭证已 `USED_UP/EXPIRED` |
| 已取消 | 订单轴 | `status='CANCELED'` |
| 退款/过期 | 两轴合并 | 订单 `REFUNDED` ∪ 凭证 `EXPIRED`（**两个来源，前端一个列表**，按时间倒序合并） |

⚠️ 不合并凭证（D4）的可见代价：**"待使用"里可能出现两条同名课**（两次购买各一张），必须展示订单号尾号或购买时间区分。VO 里给 `subTitle` 字段专门放这个区分信息。

**你问的"可购买/购买结束"和"可使用/不可使用"正是这里的两层时间**，它们作用在不同动作上、校验点不同，绝对不能合并成一列：

| 层 | 校验时机 | 不满足 | 落在哪 |
|---|---|---|---|
| ① 可购买（`sell_start/sell_end`） | 加购物车、创建订单 | "该课程已停售" | 购买链路 |
| ② 可使用（`valid_*`） | **算出 `t_entitlement.valid_until` 存下来**，之后预约时校验 | "凭证已过期" | 预约链路 |

三种 `valid_type` 里 **FOREVER 是必须有的**（D8：常年课），且 `valid_until` 存 NULL → **过期定时任务必须写 `valid_until IS NOT NULL`**，漏了这个判断，常年课会被集体误判过期退款。`valid_days` 与 `use_*` 二选一，靠 `valid_type` 决定读哪一组（不用"两者都填取交集"，那种隐式规则将来一定被误读）。

**为什么必须有 `scope` 这个显式字段**：不加它就只能靠"关联表为空"来判断"全场通用"，将来数据一多，**你分不清是"通用券"还是"配漏了范围"**。这是"用 NULL/空表表达业务语义"的通病，跟你第 14 条里 `remain IS NULL` 的表达方式一致，能显式就别隐式。

**`limit_per_user=0 表示不限` 的约定**：0 而不是 NULL 表示"不限"，因为这个列 NOT NULL 且有默认值，用 0 让"不限"和"限 1/2/3 张"在同一套整数逻辑里比较，代码里 `if (limit > 0 && got >= limit)` 一句搞定，不用判 NULL。

```sql
-- ④ 教练时段占用（D6 的核心：无排班，靠这张表 + 唯一索引防冲突）
CREATE TABLE t_coach_busy (
    id             BIGINT   NOT NULL AUTO_INCREMENT,
    coach_id       BIGINT   NOT NULL,
    store_id       BIGINT   NOT NULL,
    start_time     DATETIME NOT NULL COMMENT '整点格子起点，一行 = 一个小时',
    reservation_id BIGINT   NOT NULL,
    user_id        BIGINT   NOT NULL,
    created_at     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    KEY idx_reservation (reservation_id)   COMMENT '取消时要按预约单号一次删掉它占的所有格子'
) ENGINE = InnoDB COMMENT '教练时段占用（一行一小时）';
```

**这张表是整套时段设计的承重墙，四个要点：**

1. **一行 = 一个小时格子**，`lesson_hours=2` 的课占 **2 行**（18:00 与 19:00）。于是"同教练同时段不能两人"从**区间重叠判断**（`start < :end AND end > :start`，要锁、要事务隔离）降级成**格子存在性判断**（唯一索引，零锁）。这就是 D3"不可拆分"换来的真实收益——不是省事，是把并发难度降了一个级别。
2. **起点必须是整点**，格子才能对齐。用户只能从整点开始约，`t_course.lesson_hours` 决定占几格。
3. **生命周期**：创建预约时 INSERT → 用户取消时 DELETE → 上完课（FINISHED）**保留**（那段时间确实被占了，放出去就会双倍预约）。
4. `uk_coach_start` **同时是防冲突手段和排错手段**：如果哪天生成的格子起点不是整点（比如 18:30），它和 18:00 的格子不会冲突，唯一索引拦不住——所以**入库前的"起点必须整点"校验是业务代码的责任**，不是数据库的。这条一定要写注释。

**存 MySQL 而不是 Redis**（跟"苍穹外卖用 Redis 购物车"的区别要讲清）：Redis 购物车适合"会话级、丢了不心疼"的餐饮场景；这里的购物车要和订单确认页往返、带勾选状态、换设备还得在，**宕机就丢用户挑好的东西**，所以落 DB。代价是每次加购一次写——低频操作，无所谓（他第 12 条的判断标准）。

**结算 = 拆单 + `parent_no` 合并支付**，不引入父订单表：

```
购物车勾中 3 门课 → 同一事务建 3 张 t_booking，parent_no 相同 → 收银台一次支付
pay: UPDATE t_booking SET status='PAID', pay_time=NOW() WHERE parent_no=? AND status='UNPAID'
     影响行数 = N → 再为每张订单建凭证
```

⚠️ **秒杀商品不进购物车**（真实电商也是这样）：秒杀价格随活动变动、库存靠 Lua 抢，进购物车锁价会亏，而且"批量抢秒杀"违背秒杀的意义。秒杀仍走 `/seckill/book` 那条 Lua + MQ 链路。

**三个关键设计判断（这三条是本轮评价设计的全部价值）：**

1. **软删 + `uk_order` = "可删不可改"**。如果真 `DELETE`，唯一索引就不拦了，用户删掉再评一次等于变相修改。所以删除只是 `status=0`，行还在，索引还在，新评仍撞键。
2. **评价表为什么放 yd_order 而不是 yd_course**：写评价要校验"这单已支付、这单还没评过"，数据全在订单库 → 零跨库；统计汇总列（`rating_sum/count`）跟 `t_rating` 同事务更新才安全。**如果放 yd_course，就变成"写课程库的汇总列 + 校验订单库的支付状态"，那才需要分布式事务**——他第 20 条明确要避免。读侧（课程详情页展示评价、门店列表显示评分）跨服务，用 Feign 批量取分 + 失败降级"暂无评分"，跟他已有的"排行榜批量补昵称失败降级神秘运动者"一模一样。
3. **贝叶斯分不落库**。`(C*M + Σ) / (C + n)` 里 `C`（可信样本数，取 20）和 `M`（全站均值）**是可调参数**，存成列就锁死了，改参数要刷全表。所以：`rating_sum`/`rating_count` 落库（不可重建的原始数据），**贝叶斯分查询时用一条 SQL 现算**，`M` 用 `SELECT AVG(...)` 或全局配置。展示分给算术平均 + 条数（用户要看真实口碑），**只有排序、"优选门店"标签、首页推荐用贝叶斯分**（防"1 人打 5 星排第一"和"1 人打 1 星被踩死"两个方向）。
   教练评分同样只在 `coach_id` 非空的那条评价里计入 `t_coach_rating_stat`，一单最多计一位教练——这是 D10"一单一评"和"要评教练"两个要求的兼容解法。

## 4.3 DTO / VO 字段设计

### 4.3.1 分层与命名约定（沿用现状，不做激进调整）

```
*-api 模块：只放「跨服务契约」——Feign 接口 + DTO（如 CourseClient/BookingClient 用到的）
业务模块 model/dto：本服务入参，带 validation 注解
业务模块 model/vo：本服务出参，只放前端要展示的字段
禁止：Map 裸传（他已在 10-10 重构成 DTO，继续守住）；VO 直接返回实体（会漏出 password/status 这类字段）
```

**全局响应约定**（写进文档，前后端一起遵守）：

| 约定 | 规则 | 理由 |
|---|---|---|
| 金额 | VO 用 `BigDecimal`，同时给一个 `xxxText`（如 `payAmountText:"¥68.00"`） | 前端多处要格式化，别每个页面各写一遍 `toFixed(2)` |
| 时间 | VO 用 `String`，后端统一格式化（`yyyy-MM-dd HH:mm` 或 `HH:mm`） | 前端处理 `LocalDateTime` 序列化很痛苦，且各页面格式不同 |
| 状态 | **成对给 `status` + `statusText`** | 状态枚举文案是业务规则，不该让前端维护字典表 |
| 布尔/枚举 | 灰态、不可用一律给**枚举字符串 `reason`**，不给裸布尔 | 见 4.3.3 |
| 可操作按钮 | VO 里给 `actions: List<String>`，后端算好 | 见 4.3.3，这是本项目 VO 设计的第一原则 |

**`SlotPageVO`**（第 3、5、7 条的落点，接口 3 的响应）

```
SlotPageVO
├─ date: "2026-10-14"
├─ storeId, storeName
├─ openText: "09:00 - 21:00"        ← 展示用，前端画时间轴边界
├─ lessonHours: 1                    ← 本课程一节几小时（决定格子分组）
├─ my: MyEntitlementVO               ← ★ 页面级信息只放一次，不塞进每个教练
│   ├─ bought: true
│   ├─ entitlementId: 1024
│   ├─ totalTimes: 2 / usedTimes: 1 / remainTimes: 1
│   ├─ unlimited: false
│   ├─ validUntilText: "2026-11-13 前可用"   ← FOREVER 时给"长期有效"
│   └─ canBook: true                 ← 后端综合判断（有凭证+有效+有次数+课在本店可售）
└─ coaches: List<CoachSlotVO>
     ├─ coachId, coachName, coachTitle, avatarColor
     ├─ totalSlots: 12, freeSlots: 7
     ├─ maxContinuousFree: 3         ← ★ 最长连续空闲小时数
     ├─ nextFreeAt: "18:00"          ← ★ 支撑"点不到的格子告诉你最早几点"
     └─ slots: List<SlotItemVO>
          ├─ startText: "18:00"      ← 整点，只给起点，终点由 lessonHours 推
          ├─ endText: "19:00"
          ├─ available: true
          ├─ reason: null | "CLOSED" | "BOOKED" | "SELF_USED" | "NO_ENTITLEMENT"
          ├─ groupSize: 2            ← lessonHours=2 时这一格属于第几组（前端分组渲染）
          └─ bookableFromIndex: 0    ← 该组内从第几格开始可选，避免半组可选的歧义
```

**四个字段必须讲清"为什么"，否则前端一定会写歪**（这是我要重点教的部分）：

1. **`reason` 是枚举不是布尔**。前端要区分四种灰态文案：超出营业时间 / 被他人占用 / 我自己已经约了 / 我还没买课。**布尔只能显示"不可约"，用户会反复点同一个格子并认为页面坏了。** 后端多给一个字符串，省掉一整轮客服和一轮前端猜接口。
2. **`my` 放在页面级，不放进每个 `CoachSlotVO`**。剩余次数对同一时刻的所有教练都相同；塞进 10 个教练对象里 = 10 份重复数据 + 10 份潜在不一致（某份没更新到）。**字段归属原则：页面级信息挂页面，条目级信息挂条目。**
3. **`maxContinuousFree` + `bookableFromIndex`** 是 D3（不可拆分）的直接产物。`lessonHours=2` 时，一个"18:00 空、19:00 被占"的教练，18:00 那格**不能选**（放不下 2 小时）；所以要把格子按组划开（`groupSize`），并且每组要么整组可选要么整组不可选。**如果前端自己算这个分组，一定会在边界上出 bug。** 后端算好、前端只渲染。
4. **`nextFreeAt`** 支撑他第 5 条想要的体验："A 教练 18:00 下课，用户想约 17:50" → 在我们的模型里 18:00 之前的格子已被 A 占到 18:00，用户点 17:00 那格（`reason=BOOKED`），前端直接把 `nextFreeAt:"18:00"` 显示成按钮副标题"最早 18:00 可约"。**用户不需要理解什么叫整点，但他一眼就知道该点哪。**

**`BookingDetailVO`**（第 8 条：像真实电商）

```
orderNo, status + statusText（"待支付"/"已完成"/"已退款"…）, parentNo, isFromCart
courseId, courseName, courseKind, lessonHours, saleType, timesGranted
storeId, storeName, storeAddress          ← 地址来自 Feign 批量查门店，失败则不显示行
unitPrice + unitPriceText, quantity
couponTitle, discountAmount + discountAmountText, payAmount + payAmountText
createdAt/paidAt/canceledAt/refundAt（全部后端格式化字符串）, cancelReason
entitlements[]: {entitlementId, status + statusText, totalTimes, usedTimes, remainTimes,
                 validUntilText, reservations[]: {startText, coachName, status}}
actions: [PAY | CANCEL | BOOK | RATE | AGAIN | DELETE]
```

- `entitlements[]` 是**嵌套**：一张订单出 N 张凭证，每张凭证下挂它的预约记录。电商订单详情页"商品行 → 售后状态"就是这个结构，用户一眼看到"我买了 3 次，约了 1 次，还剩 2 次"。
- **`actions` 是后端算的**（本项目第一 VO 原则）：预约按钮 = 已支付 ∧ 凭证 ACTIVE ∧ 有剩余次数 ∧ 未到 `valid_until` ∧ 该课在本店在售。这套规则有 5 个条件，前端重复实现一遍就是 5 个出错点；后端改规则时前端永远慢一拍。
- `RATE` 的出现条件 = `status=PAID` 且 `t_rating` 无该单 → 后端查一次给布尔，比前端"进详情页再单独调评价校验接口"省一次往返。

**`MineSummaryVO`**（第 9 条四宫格）

```
unpaidCount（订单轴）, waitUseCount（凭证轴 ACTIVE 且有余次）,
bookedCount（预约轴 BOOKED 且 start>now）, ratingCount（待评价）
```
四个 count 一次给全，**别做 4 个接口**——首页四宫格并排显示，4 次请求必然出现数字互相跳动。跨三张表 4 条 `COUNT`，都在 yd_order，一次请求串行 4 条走索引的 count 完全够（低频、每页数一次）。

### 4.3.4 管理端 DTO（D1/D9/D3 的表单联动）

`CourseSaveDTO`：`id?, name, type, kind, lessonHours(1|2|3), saleType(TIMES|UNLIMITED), timesPerBuy, duration, calories, price, tags, coverColor, description, suitable, status, stores[]:{storeId, sellStartTime, sellEndTime, validType, validDays, useStartTime, useEndTime}, coaches[]:coachId, videos[]:videoId`

**管理端表单三条必须实现的联动**（否则数据一定会配错，且配错了接口还返回 200）：

1. **`saleType=UNLIMITED` 时隐藏并禁用 `timesPerBuy`**（不限次没有"给几次"的意义）。
2. **`validType=DAYS` 只显示 `validDays`；`RANGE` 只显示 `use_start/use_end`；`FOREVER` 两个都不显示**。用 `v-if` 切，**不要三个都显示让人随便填**——三者同时有值时后端读哪个都是隐患（这也是我把前面"两者取交集"的想法否掉的原因，隐式规则一定会被误读）。
3. **`lessonHours` 用 `el-select`（1/2/3）而不是数字输入框**：这个值参与格子分组，填 90 会让整点模型失效且数据库不会报错。

`CouponSaveDTO` 同理：`couponType=SECKILL` → 显示 `total/remain/limitPerUser(≥1)`；`NORMAL` → 全部隐藏、`limitPerUser=0`。`scope=1` 才显示课程多选，`scope=2` 才显示门店多选。**表单联动 = 数据正确性的第一道防线，别指望后端校验兜住所有配错**（后端校验仍要写，但用户面对的是表单）。

### 4.3.5 规则说明的策略模式（D21）

不同课程形态、两种券的规则条目差别很大（按次课要讲"几次/怎么用/过期怎么办"，不限次课要讲"随便约"，秒杀券要讲"限领几张/库存有限"）。如果写成 `if (saleType==...) else if (...)`，六七个场景每个 4~6 行文案，最后是一个 30+ 分支、谁加类型都要改同一个方法的大函数。所以用**策略模式**：一个接口 + 按场景码注册的实现类。

```java
/** 规则说明生成策略：按场景码选出实现，产出"给用户看的规则条目" */
public interface RuleDescribeStrategy {
    /** 本策略负责的场景码，取值见 RuleScene 枚举 */
    String scene();

    /** 生成规则条目：每个元素是一行完整文案，前端直接渲染成列表 */
    List<String> describe(RuleRuleContext ctx);
}
```

**场景码（`RuleScene` 枚举，6 个起步）**

| scene | 用在 | 典型条目 |
|---|---|---|
| `COURSE_TIMES` | 按次售卖的可售课 | "本课程一次购买得 N 次"／"预约成功不扣次，到点未取消视为已消费"／"距开课 1 小时内不可取消"／"有效期至 X，过期未用完的次数不退" |
| `COURSE_UNLIMITED` | 不限次可售课 | "有效期内不限次预约，每次一节"／"同一时段每位教练仅接待一位会员"／"长期有效，不过期" |
| `COURSE_CONTENT` | 展示型课程 | "本课程为免费跟练内容，无需购买"／"可发表评论与回复，删除后不可恢复" |
| `COUPON_SECKILL` | 秒杀券 | "限量 N 份，领完即止"／"每人最多领 M 张"／"一单只能使用一张"／"领后 X 天内有效" |
| `COUPON_NORMAL` | 普通券 | "不限量领取"／"满 Y 元可抵扣 Z 元"／"仅限指定课程/门店可用" |
| `RESERVATION_CANCEL` | 预约页取消规则 | "提前 1 小时以上可取消"／"取消不扣次数，时段自动释放" |

**注册与选取**：实现类都标 `@Component`，工厂把 Spring 注入的 `List<RuleDescribeStrategy>` 按 `scene()` 转成 `Map`；找不到对应场景就退回 `RuleScene` 的默认实现并打 `warn` 日志（**新增类型时忘了写策略，要能看见，不能静默返回空文案**）。

**三条必须守住的分寸**（这三条是这个模式不烂掉的前提）

1. **策略只产出文案，不做数据库查询、也不做校验。** `RuleRuleContext` 由调用方把已经查好的字段（`lessonHours`、`saleType`、`timesPerBuy`、`validUntil`、`limitPerUser`…）填进来。**校验逻辑留在 service 里**——如果把"能不能用这张券"也塞进策略，将来改文案就等于改校验，规则会跟着文案一起漂移，这是最难查的一类 bug。
2. **公共条款只写一份**，放常量类 `RuleTextConstants`（如"一单只能使用一张券""取消不扣次数"这类跨场景重复出现的话术），策略里引用常量而不是各写一遍。散落硬编码的后果是同一规则在课程页和券页文案不一致。
3. **不落库、不做规则引擎。** 文案要能被 review、能被单测、能跟着代码一起回滚。"运营在后台自己配文案表达式"听起来灵活，实际会把一个 `List<String>` 需求做成解释器——超出本轮需要，也超出你要面试讲清的范围。

**VO 落点**：详情页给 `ruleTexts: List<String>`（整块规则弹窗直接渲染），列表页只给一句 `ruleSummary`（如"2 小时/节 · 一次 2 次 · 领后 60 天有效"）。**列表页不要带完整 `ruleTexts`**——列表一次返回 10~20 条，每条几行文案，白占带宽，而且列表页根本不会展开给用户看。

## 4.4 关键流程（含每步注释要求）

### 流程 B · 查可约时段（读侧，无并发防护）

```
输入：courseId, storeId, date
① 校验课程在本店在售（t_course_store）
② 查该课在本店可约教练：
   SELECT c.* FROM t_coach c
     JOIN t_coach_course cc ON cc.coach_id = c.id
    WHERE cc.course_id = ? AND c.store_id = ? AND c.status = 1
   -- 一次查完，不在循环里查库（沿用 CommunityServiceImpl 里 IN 查询的正确写法）
③ 查这些教练当天全部占用格子（一次查完，不是每人一次）：
   SELECT coach_id, start_time FROM t_coach_busy
    WHERE coach_id IN (...) AND start_time >= 当天00:00 AND start_time < 次日00:00
   → 组装 Map<Long, Set<LocalDateTime>>
④ 内存里为每个教练生成格子：
   小时区间 = max(门店 open_start_hour, 教练 work_start_hour)
            ~ min(门店 open_end_hour,     教练 work_end_hour)
   当天星期不在 work_days → 该教练整天空闲格数 0（VO 给 reason=CLOSED + 文案"本周不排班"）
   从起始整点逐小时推进；起点必须 ∈ work_days 当天
   连续空闲统计 = 扫一遍小时线，遇到被占就归零，取最大值 → maxContinuousFree
   lessonHours=H 时：起点 s 可选 ⟺ s..s+(H-1) 全部空闲；否则该组全部标 reason=BOOKED
   nextFreeAt = 第一个空闲起点
⑤ 组装 SlotPageVO（my 字段单独查 t_entitlement 汇总）
```

**"一次查完 + 内存算"** 是这个流程的全部要点：全程只有 2 条 SQL（教练、占用），没有循环查库、没有并发防护、没有 Redis。**读简单、写严格**——冲突只在创建预约时防。这个分工是他这个项目该有的复杂度分布。

### 流程 C · 创建预约（写侧，唯一索引防冲突）

```java
/** 预约成功 = 占住 H 个整点格子 + 落一张预约单，全部在 yd_order/yd_course 同库事务内 */
@Transactional(rollbackFor = Exception.class)   // 注：t_coach_busy 和 t_reservation 都在 yd_order
public ReservationVO book(Long userId, ReservationCreateDTO dto) {
    // ① 查凭证（校验归属：WHERE id=? AND user_id=?，杜绝用别人的凭证）
    // ② 校验课程与门店匹配（凭证的 course_id/store_id == 请求的）
    // ③ 校验次数：total_times IS NULL OR used_times < total_times
    // ④ 校验有效期：valid_until IS NULL OR valid_until > start_time   ← 两个 NULL 判断都不能少
    // ⑤ 校验教练会这门课：t_coach_course 存在 (coachId, courseId)
    // ⑥ 校验起点合法：整点、在门店与教练营业时间交集内、H 格都放得下
    // ⑦ 按 start_time 升序逐格 INSERT t_coach_busy（H 行）
    //    捕获 DuplicateKeyException → 抛"该时段刚刚被预约，请刷新后重试"
    //    → 事务回滚，前面已插入的格子自动释放（不需要手写补偿代码）
    // ⑧ INSERT t_reservation（时间/教练名/门店名快照、cancel_deadline、verify_code）
    // ⑨ 发站内通知（notify.booking）
}
```

**两个必须写进注释的细节：**

- **⑦ 的升序插入不是洁癖，是防死锁**。两个用户抢 [18,19] 和 [19,18] 这种交叉顺序时，如果允许乱序插入会形成加锁环。升序插入让所有事务按同一顺序拿锁。这个规则值得写在方法注释里，因为将来有人重构循环方向就会踩。
- **回滚由 `@Transactional` 自动完成，不需要补偿代码**。这正是同库的好处，也是第 20 条"避免分布式事务"能成立的原因。**对照旧链路 B**：旧模型里"占名额"是跨服务 Feign（order → course），所以必须手写三处补偿；新模型里占用和预约单同库，事务自动回滚。**删掉的是代码，也是 bug。**

唯一索引的作用范围要写清：**它只保证"同一教练的同一个整点不被两次 INSERT"**。起点若不是整点（脏数据）它就拦不住，所以⑥的整点校验是业务代码的责任。

### 流程 D · 取消 / 到点自动消费（D5 落点）

**取消**（用户主动，一句 CAS，不在 Java 里算 1 小时）：

```java
// UPDATE t_reservation SET status='CANCELED', cancel_reason=?
//  WHERE id=? AND user_id=? AND status='BOOKED' AND cancel_deadline > NOW()
// 影响行数 0 → 三种可能：不属于自己的单 / 状态不对 / 距开课不足 1 小时 → 统一提示"无法取消，请检查是否距开课不足 1 小时"
// 成功后：DELETE FROM t_coach_busy WHERE reservation_id=?   ← 教练时段回到空闲（你要的效果）
```

**到点自动消费**（定时任务，每分钟）：

```sql
-- 第一步：圈出到点的单（命中 idx_settle）
SELECT id, entitlement_id, user_id, course_id FROM t_reservation
 WHERE status = 'BOOKED' AND start_time <= NOW();
-- 第二步：逐条 CAS 置 FINISHED，status 条件就是幂等锁
UPDATE t_reservation SET status='FINISHED', finished_at=NOW() WHERE id=? AND status='BOOKED';
-- 影响行数 1 才继续（别的实例/上一轮已经处理过就跳过）
-- 第三步：扣一次（到点未取消 = 消费，D5）
UPDATE t_entitlement SET used_times = used_times + 1,
       status = CASE WHEN total_times IS NOT NULL AND used_times + 1 >= total_times
                     THEN 'USED_UP' ELSE status END
 WHERE id = ? AND status = 'ACTIVE';
```

- **不扣次的规则自动成立**：取消走 CANCELED 分支，永远不会进入这个任务的扫描条件 → 不扣次。**你要的"取消不扣次"是免费的。**
- 到点判定用 `start_time`（照你的原话"18:00 没取消就算消费"）。备选是 `end_time`（2 小时的课要上完才扣）——放在 4.12 让你确认，实现只差一个字段。
- 三步里每一处 UPDATE 都带 `status` 条件 → **任务重跑安全，多实例并发安全**，不需要引入分布式锁（第 12 条）。
- **`t_coach_busy` 的行不删**：那段时间真被占了，放出去会双倍预约。只有取消才删。

### 流程 E · 评价与删除

```
POST /api/rating/save {orderNo, score, comment, coachId?}   ← @Idempotent 防双击
① 校验订单：WHERE order_no=? AND user_id=? AND status='PAID'（已退款/已取消不可评）
② 若给了 coachId：校验该教练出现在这单的某个 FINISHED 预约里（防乱评一个陌生教练）
③ INSERT t_rating —— uk_order 撞键 → "本单已评价过"
④ 同事务 UPSERT 三张汇总：
   INSERT t_store_rating_stat(store_id, rating_sum, rating_count) VALUES(?,?,1)
   ON DUPLICATE KEY UPDATE rating_sum = rating_sum + ?, rating_count = rating_count + 1;
⑤ 通知

DELETE /api/rating/delete → UPDATE t_rating SET status=0 WHERE id=? AND user_id=?
   + 同事务 UPSERT 回退（rating_sum - score, rating_count - 1）
   ★ 行保留 → uk_order 仍生效 → 删了不能再评（这就是"可删不可改"的实现）
   ★ 回退要用原 score，所以第②步必须先 SELECT 拿到 score 再改 status
```

**读取侧**：门店/课程/教练的分数一律 **查询时算贝叶斯**，不落库。`C=20`、`M=全站平均` 做成配置项放 `application.yml`（注释写清"改这两个数就是调整新店的收缩强度，无需刷历史数据"）。

### 流程 F · 过期与退款（D7 + D8，每小时）

```sql
SELECT id, order_no, used_times FROM t_entitlement
 WHERE status='ACTIVE' AND valid_until IS NOT NULL AND valid_until < NOW()   -- ★ NULL 判断必须有，否则常年课集体误判
 LIMIT 200;                                                                  -- 分批，注释写"单轮最多处理 200 张，防止一次锁太久"
UPDATE t_entitlement SET status='EXPIRED' WHERE id=? AND status='ACTIVE';     -- CAS，0 行 = 已处理，幂等
-- used_times = 0 → UPDATE t_booking SET status='REFUNDED', refunded=1, refund_at=NOW() WHERE order_no=?
-- used_times > 0 → 订单不动（剩余不退）
```

券：`t_user_coupon.status='USED'` 的券**过期不退**（一次性消耗品，注释写明这个规则）。
钱：不调任何支付接口，只置状态 + 前端显示"已退款"。**不预留支付网关口子**（你的第 3 条明确要求，符合"别为假设的未来需求设计"）。

### 流程 G · 领券（D9 两条分支）

```
SECKILL 券：Redis Lua（库存 DECR + Hash 限领计数）+ 发 MQ 异步建 t_user_coupon
NORMAL  券：SELECT COUNT(*) 判限领（0=不限）→ 直接 INSERT。低频操作，不用 Redis（第 12 条三档标准）
```

秒杀券 Lua 扩两行（仍是他学过的 Lua，不是新机制）：

```lua
-- KEYS[1]=coupon:stock:{id}  KEYS[2]=coupon:got:{id}(Hash: field=userId, value=已领张数)
-- ARGV[1]=userId  ARGV[2]=TTL秒  ARGV[3]=limit（0=不限）
local limit = tonumber(ARGV[3])
if limit > 0 then
    local got = tonumber(redis.call('HGET', KEYS[2], ARGV[1]) or '0')
    if got >= limit then return 2 end          -- 超过每人限领
end
if tonumber(redis.call('GET', KEYS[1]) or '0') <= 0 then return 1 end   -- 已抢完
redis.call('DECR', KEYS[1])
redis.call('HINCRBY', KEYS[2], ARGV[1], 1)
redis.call('EXPIRE', KEYS[1], tonumber(ARGV[2]))
redis.call('EXPIRE', KEYS[2], tonumber(ARGV[2]))
return 0
```

（原实现的 `SISMEMBER`/`SADD` 换成 `HGET`/`HINCRBY`，因为现在要的是"次数"不是"有没有"。）

**①→⑤ 的顺序是这套设计里唯一的"反直觉点"，必须注释清楚**：你说"加积分先操作 Redis"，我主张**反过来**。原则一句话——**不可重建的先落库，可重建的最后写缓存**。Redis 加了分但 DB 失败：榜上有分、账户没钱，用户投诉时查无实据；DB 成功 Redis 失败：榜少一分，回填任务能修正。**故障后果的可修复性，决定写入顺序。**

## 4.5 缓存与 Redis（三件套补齐）

| 目标 | 手段 | 现状 | 要做的 |
|---|---|---|---|
| 防击穿 | 逻辑过期 + Redisson 互斥 + 线程池异步重建 | ✅ 已实现 | 锁改独立 key + `tryLock(0, 10, SECONDS)` |
| 防穿透 | 空值缓存（TTL 2min） | ✅ | 保留；**不加布隆过滤器**（数据量不需要，且要处理删除，违反第 12 条） |
| 防雪崩 | **物理 TTL + 随机抖动** | ❌ `writeCache` 用的是不带 TTL 的 set，key 永久堆积 | `set(key, val, BASE_TTL + random)`，**物理 TTL = 逻辑 TTL × 1.5~2**：物理比逻辑晚过期，所以不会提前砸 DB（逻辑过期先触发），又能自然回收 |

**重建用线程池不用 MQ**（回答你第 10 条的问句）：MQ 的价值是跨服务 + 削峰 + 重试；缓存重建是进程内的异步，走 MQ 会新增"重建消息丢了 → 缓存永不更新且没人知道"这个更难查的问题。项目里已有 `cacheRebuildExecutor`（`DiscardPolicy`，队列 64），**丢弃是正确策略**：任务丢了下一轮逻辑过期会再触发，比堆积更省内存。逻辑过期允许短暂读旧数据，你已经理解对了。

**预热顺序采纳你的想法，并补一条**：定时任务先 `SET` Redis 库存、**再** `UPDATE ... SET status=1 WHERE status=0` 翻状态。这样绝不会存在"状态已开放但库存未就绪"的空窗。⚠️ 但**重复预热时不能 `DEL seckill:bought:{id}`**（现在 `preheat()` 里就删了它）——那会把"一人一单"的资格清空，抢过的人能再抢一次。只在 status 从 0→1 的那一次 CAS 成功分支里才允许写库存和资格 key。

**新增/变更的 Key**：

| Key | 类型 | 用途 | TTL | DB 兜底 |
|---|---|---|---|---|
| `login:token:{jti}` | String | JWT 有效性白名单 | = token 剩余有效期 | 丢了 = 全站重新登录（fail-close 的后果，见 4.6） |
| `login:user:{userId}` | Set | 该用户所有在线 jti，禁用时批量删 | 同上 | 可从 DB 重建不了（正常，重新登录即可） |
| `point:check:{userId}` | Bitmap | **一人一 key**，offset = 距基准日天数 | 永久（可设 400 天） | ✅ `t_checkin_record`（新增） |
| `rank:month:{yyyyMM}` | ZSet | 月榜实时 | **归档后设 40 天** | ✅ 可从 `t_points_log` 重算 + `t_rank_archive` |
| `coupon:got:{id}` | **Hash** | field=userId value=已领张数（替代 Set） | 到领取截止 | ✅ `t_user_coupon` 可重建 |
| `store:geo` | GEO | 门店坐标 | 永久 | ✅ `t_store`（启动重建，已有） |
| ~~`community:following:{userId}`~~ | Set | **建议废弃**：它只在 `follow()` 写、`isFollowing` 读 DB，是"既当缓存又当唯一数据源"的反模式 | — | `commonFollow` 改查 DB |

## 4.6 Sentinel + 令牌白名单

**限流（你选：网关 + dashboard + 规则持久化）的落地清单与三个坑**：

1. **依赖**：`spring-cloud-starter-alibaba-sentinel` + `spring-cloud-alibaba-sentinel-gateway`；SCA 2023.0.3.3 对应 Sentinel 1.8.7。
2. **必须先补 `spring-cloud-starter-alibaba-nacos-config`**——现在项目只引了 `nacos-discovery`，**规则持久化到 Nacos 没有 config 客户端读不到**。这是一处真实的依赖缺口，不是配置项问题。
3. **⚠️ 端口冲突**：`sentinel-dashboard` 默认监听 **8080**，而网关已经占了 8080。启动必须 `-Dserver.port=8858`，VM 安全组开 8858。
4. **⚠️ Nacos 数据源是单向只读**：在 dashboard 上改规则**不会回写 Nacos**，进程重启就没了。所以约定：**规则以 Nacos 配置为唯一真相，dashboard 只用来观察实时流量**。这条一定要写在文档里，否则你一定会困惑"我明明改了怎么重启就恢复"。
5. **⚠️ 网关需要 `spring.cloud.sentinel.eager=true`**，否则不主动向 dashboard 注册、控制台看不到应用。
6. 规则落点：`yd-gateway-flow-rules`（Nacos JSON）；先给 `/api/seckill/**`（QPS 单接口阈值）、`/api/booking/create`（阈值 + 参数限流按 userId）、`/api/behavior/report`（匿名接口，必须限）。
7. **`@Idempotent` 注解 + AOP 放 fitness-common**，不依赖 Sentinel（幂等是业务正确性，限流是容量保护，**两件事别混**）。
   - 注解字段：`prefix`（业务前缀）、`expireSecond`（窗口秒数，注释写"为什么取这个值"）、`message`（用户可见文案）。
   - key：`idempotent:api:{prefix}:{userId}:{requestURI}`（**一期不上 SpEL**，可读优先；将来要按业务号幂等再扩一个 `keyParam` 走简单参数名取值）。
   - 切面：`setIfAbsent(key,"1",Duration.ofSeconds(expireSecond))`，`false` 就抛 `BusinessException`；**不主动删 key**，语义就是"X 秒内不许重复提交"。
   - 要加的接口：领券、评价、加购、创建预约、秒杀。**下单不加**（下单有 `uk` + 状态 CAS 兜底，加幂等反而挡住"用户真心想再买一单"）。
   - 顺带说明：这套 AOP **你在「生活工具」里已经写过一遍**。那目录不在当前工作区（刚才读被权限拦了），要是想照搬自己那版实现（面试时更站得住），授权我读一次或你把类贴过来。

**令牌白名单**（D15，修 P0-2 / P1-8）：

```
登录：jti=UUID 写入 JWT claim（现在只有 subject=userId，必须加）
      SET login:token:{jti} = userId, TTL=token 有效期;  SADD login:user:{uid} {jti}
网关：验签 → EXISTS login:token:{jti}；不存在 → 401
      ★ 顺手修 deny()：403 场景（/inner、无权限）返回 403，鉴权失败才返回 401
管理端：同机制，前缀 admin:login:，一并解决"角色写进 token 12 小时不可撤销"
```

**必须提前决定的取舍**（别等出事）：Redis 不可用时 fail-open（跳过校验、签名对就放行，禁用暂时失效）还是 fail-close（全部拒绝，故障半径=全站下线）。**建议 fail-close** + Redis 开 AOF（compose 里已开），并且**这个决定要写在网关代码注释里**——面试问"你的方案有什么代价"，能答出"我把可撤销性换成了 Redis 可用性，并明确选择了 Redis 挂时宁可全站下线"就是满分回答。

| K2 | **列表一律游标分页**，接口只收 `cursor + size`，返回 `nextCursor`，不再有 `page` | 推荐流用"小时桶"保证翻页不重复 |
| K3 | **可见性三档都做**：公开 / 仅好友 / 私密 | "仅好友"用拉模式查互关好友，**绝不进推模式扩散** |
| K4 | 底部导航**加第 5 个 tab**（首页/社区/预约/购物车/我的） | 前端侧，工作量在他那边 |

### K1 浏览量：三层各有角色，任何一层丢了都能从下一层重建

| 层 | 存什么 | 丢了怎么补 |
|---|---|---|
| Kafka / `t_behavior_log` | 原始浏览事件（明细，可重放） | 从明细重算 |
| Redis `post:view:delta`（Hash，field=postId） | **未刷的增量** | 从 DB 账本继续累加，不影响正确性 |
| MySQL `t_post.view_count` | **账本（真相）** | 不可丢 → 所以它是真相 |

两个必须写对的细节：

1. **"刷完删除 Redis"是有 bug 的**：`GET → 写 DB → DEL` 之间新产生的浏览会被 DEL 掉，永久少计。
   必须用 **`GETDEL`（原子取出并清空，Redis 6.2+）**，或读增量后 `HINCRBY field -delta` 原子减。
   刷库语句必须是 `view_count = view_count + delta`，**不能 `= Redis 的值`**（会覆盖刷库间隙已落库的数）。
2. **浏览量参与排序 + 异步廉价计数 = 刷量即上榜**。解法正好复用 behavior：
   浏览事件幂等键取 `userId:postId:日期`，靠 `uk_event` 让"一人一帖一天只计一次"。

**为什么不新开一条 view topic**：计数本身一次 `HINCRBY` 就够，不需要异步；
Kafka 的价值是"留原始明细、可重放"，而 `fitness-behavior` 已经在做这件事。
多一条链路就是多一套 consumer、多一套失败分支——**已知能力能复用时不要新建**。

### K2 分页：三种流三把游标（offset 一律不用）

- **时间线类**（关注流、我的、收藏、点赞）：keyset `WHERE (publish_time, id) < (#{t}, #{id}) ORDER BY publish_time DESC, id DESC LIMIT n`，
  配 `(visibility, status, publish_time, id)` 索引。MySQL 支持这种行构造器比较，**永不重复永不漏**。
- **推荐流**：分数含时间衰减，`hours_since_post` 每小时都在变，严格 keyset 会漂。
  **把小时数取整进分母**（同一小时内分数完全不变），游标变 `(score_bucket, score, id)`。
  代价是一小时内榜不刷新，换来翻页稳定 —— 一行代码的改动，比"快照游标"少一套要维护的缓存。
- **二级评论"更多回复"**：`(id ASC)` 游标，天然稳定。

### 推荐公式（能背、每一项都能解释）

```
hot   = 收藏×5 + 评论×3 + 点赞×2 + 浏览×0.2
score = log10(hot + 1) / pow(hours_since_post + 2, 1.5)
```

- 权重按**用户付出成本**排：点一下 < 写一句 < 收藏（收藏=我要留着，意图最强）；浏览最廉价且最易刷，给 0.2，甚至建议**只展示不参与排序**。
- `+2` 是新帖保护（避免分母为 0 就冲顶）；`1.5` 是 gravity，越大沉得越快。
- `log10` 压量级：不然 1 万浏览和 10 万浏览差 10 倍权重。
  这和贝叶斯评分是同一类问题：**分数要防"样本量"和"极端值"两个方向**。

### K3 可见性：难点不在存，在查

`visibility ∈ {PUBLIC, FRIEND, PRIVATE}` 一列就够，但"仅好友"要的是**互关**（现有 `t_follow` 单向）。
如果把它塞进公共列表，查询会变成
`visibility=PUBLIC OR (visibility=FRIEND AND author_id IN (互关集合)) OR author_id=我`
—— 这种 OR + IN 在 MySQL 里基本用不上索引。按流分工就绕开了：

| 场景 | 装什么 | 怎么查 |
|---|---|---|
| 推荐（陌生人） | **只装 PUBLIC** | 推荐池天然干净，不判可见性 |
| 关注流（推模式收件箱） | 扇出时**只写 PUBLIC** | 直接读 `feed:inbox` |
| **好友动态**（新 tab） | PUBLIC + FRIEND | 拉模式：`author_id IN (互关好友) AND visibility IN (PUBLIC,FRIEND)`，走 `idx_author_time` |
| 个人主页 / 我发布的 | 含 PRIVATE | `author_id=我`，不用过滤 |

- **不要为"好友"新建关系表**：那会引入"关注/取关要双向同步"的一致性问题。用两个 `EXISTS` 查 `t_follow` 即可。
- 明确写进注释、别留给以后：**取关后已扇出到对方收件箱的 PUBLIC 内容不撤回**（一期不做撤回）。

### 评论与点赞收藏

- `t_post_comment` 一张表、两级封顶，**必须带 `root_id`**（一级的 root_id=0）：
  否则"展开某个一级评论下的 100 条回复"要递归查询。只有两级 —— 无限树要递归、手机上缩进不可读。
- **不匿名** ✓ 存 `user_name`/`avatar_color` 快照（跨库 + 高频读 + 要历史原值）。
- 一期**不给评论加点赞**（连字段都不留，加了就是一列计数 + 一张关系表 + 一套幂等）。
- ⚠️ **不要和 `t_course_comment`（展示课评论）合并成一张表**：准入条件不同、统计口径不同、
  帖子评论还要判可见性。**长得像不代表是同一个东西**，这条判断我在 4.2.1 写过一次，社区回来后一定会再诱惑一次。
- **点赞、收藏两张表**（不合成一张带 `type` 的）：唯一键语义不同（合成后 `uk_post_user_type` 才能锁住"同帖既能点又能藏"）、
  计数列回退、取消动作、"我的"里两个 tab —— 合并省一张表，换来四处复杂。
- 计数用 **DB 原子 UPDATE + 关系表同一本地事务**；Redis Set 只用来加速"这一页里哪些我点过"的标记，
  **最终防线是 `uk_post_user`**。这条正是核查文档里 `community:following:{userId}`
  （既当缓存又当唯一数据源，重启后共同关注永远为空）那个错的修正版。

## 附 C · 这份代码里最值得你亲口讲清的 7 个技术点

1. **为什么"检查 + 扣减"必须放进一条 Lua / 一条 UPDATE**（`booked<capacity`、秒杀 Lua、`balance>=cost`）—— 这是并发正确性的根。项目里 6 处同构，你能一口气讲完就说明真的懂了。
2. **唯一索引是幂等的最终防线**：注册 `uk_phone`、进度 `uk_user_video`、点赞 `uk_post_user`、券 `uk_user_coupon`、流水 `uk_biz`、事件 `uk_event` —— 每一处都配一个"先查再插 + DuplicateKeyException 兜底"。
3. **逻辑过期 vs 互斥锁阻塞重建**：项目用的是前者（不阻塞、返回旧数据），黑马点评用的是后者。能对比说清"什么场景选哪个"就是加分。
4. **冗余快照的三条判断准则**：跨库读 / 高频读 / 需要历史原值。项目 9 处冗余逐个能对上号。
5. **延迟消息不撤回，靠消费时状态校验幂等**（设计文档 §4 那句括号说明，是全项目最漂亮的一句话）。
6. **Rabbit 与 Kafka 的分工**：业务指令要路由/延迟/DLX/确认 → Rabbit；高吞吐 append-only + 按 key 保序 + 可重放 → Kafka。
7. **TCC 式手工补偿**（链路 B 的第⑦⑧⑨步）：能说出"我没用 Seata，因为跨服务只有两步、补偿代价小，而且我能指出哪一步没有补偿"，比背"分布式事务有几种方案"强得多。

反过来，这几处**照旧说法讲会被戳穿**（2026-10-14 更新，情况已经不同）：

- `@Idempotent`：**基建 + 标注都有了**（领券、创建预约、加购、评价四个写接口），可以讲。
  但必须先说一句"它只挡时间窗内的重复提交，**最终防线是数据库唯一索引**"，
  否则会被追问"两次隔 3 秒的请求你拦得住吗"。
- `@RateLimit`：**仍然不存在**，Sentinel 限流本轮已明确跳过，别提要别说。
- 短信验证码登录：实现仍是密码登录，别说。
- 数据看板 `dashboard/summary`：后端仍无接口（管理端走 Mock），别说。
- 核销：**逻辑在 `ReservationService#verify`（只登记到店、不决定扣次），但对外接口还没接**——
  管理端 `/admin/reservation/*` 与 `InnerReservationController` 属于剩下的"管理端补齐"一批
  （coach CRUD、reservation 分页与核销、entitlement 分页、order/detail、dashboard/summary、course/window/*）。
  能确定的是：**订单上没有任何核销接口**，别再说"支付后核销才生效"。
