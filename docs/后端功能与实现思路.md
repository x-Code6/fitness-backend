## 一、先记住四个地基决定

后面 170 个接口全部是这四条推出来的。检查业务流程时如果某处觉得别扭，八成是它违反了这四条之一。

### 1. 课程 = 可购买的商品，不是"一场活动"

v1 把课程当活动（有 `t_course_schedule` 场次表、有容量和已报名人数）。v2 删掉了场次：
**买课买的是"上课资格"，具体什么时候上，由预约时教练的空闲时段决定。**
所以"课程能不能卖"和"这节课有没有位置"是两套完全不同的判断，别再互相引用。

### 2. 三条独立的状态机轴，分三张表

| 轴 | 表 | 状态 | 回答什么问题 |
|---|---|---|---|
| 钱 | `t_booking` | `UNPAID → PAID → CANCELED / REFUNDED` | 这单付了吗、退了吗 |
| 权益 | `t_entitlement` | `ACTIVE → USED_UP / EXPIRED` | 还剩几次课、过期没 |
| 时段 | `t_reservation` | `BOOKED → FINISHED / CANCELED` | 这节课约上了吗、上完了吗 |

★**"已过期"不是订单状态、"待上课"不是凭证状态**。v1 把它们挤在一张表里，
于是任何"这单现在算什么"的讨论都说不清。拆成三轴之后，每个动作只推自己那一条：
取消预约**不**动订单、凭证用完**不**改订单、核销**不**扣次。

### 3. 两类课程一张表 + 一个类型位（`course_kind`）

- `SALE`：线下可购买、可约教练 → 用户说的话叫**评价**（`t_rating`，要买过、带星级、进评分统计）
- `CONTENT`：展示型（看视频）→ 用户说的话叫**评论**（`t_course_comment`，任何登录用户、无星级）

★**不合并成一张表**：准入条件、有没有分值、统计口径三样都不同。
"长得像不代表是同一个东西"——这条在实现里靠 `loadContentCourse()` 每次写都判类型来钉死。

### 4. 两层时间，四列，绝不合并

`t_course_store`（课程 × 门店）上：

| 层 | 列 | 校验时机 | 不满足时 |
|---|---|---|---|
| ① 可购买 | `sell_start_time / sell_end_time` | 建单与试算时 | "该课程已停售" |
| ② 可使用 | `valid_type / valid_days / use_start_time / use_end_time` | 只用来**算出**凭证的 `valid_until`，之后预约时校验 | "凭证已过期" |

★`valid_type = FOREVER` 会让 `valid_until` 存 **NULL**，
于是所有过期判断都必须带 `IS NOT NULL`——漏一处的后果是常年课被集体误判过期退款。
这类 bug 测试里很难发现，所以每个判断点都写了注释。

## 二、服务拓扑

| 模块 | 端口 | 数据库 | 中间件 | 职责边界（一句话） |
|---|---|---|---|---|
| `fitness-gateway` | 8080 | — | Redis | 唯一入口：路由、JWT 校验、jti 令牌白名单、CORS |

| `fitness-course` | 8102 | `yd_course` | Redis, RabbitMQ, MySQL GEO | 课程 / 门店 / 教练 / 视频 / 秒杀活动 / 优惠券 / 展示课评论 |
| `fitness-order` | 8103 | `yd_order` | Redis, RabbitMQ, MySQL | 下单试算 / 订单 / 凭证 / 时段 / 预约 / 评价 / 看板统计 |
| `fitness-point` | 8104 | `yd_point` | Redis, RabbitMQ | 打卡 / 积分流水 / 商城兑换 / 排行榜与归档 |
| `fitness-behavior` | 8106 | `yd_behavior` | Redis, Kafka | 埋点接收（Kafka 生产）+ 明细落库 + 热度榜 |
| `fitness-community` | 8105 | `yd_community` | Redis, RabbitMQ, Kafka | 动态 / 互动 / 两级评论 / 关注 / Feed 分发 |
| `fitness-admin-server` | 8107 | `yd_admin` | Redis, MySQL | 管理端 BFF：RBAC、操作日志、跨服务聚合、文件上传 |
| `fitness-common` | — | — | — | 统一响应/异常/错误码、Redis 与 MQ 常量、`@Idempotent`、`UserContext` |
| `fitness-*-api` ×4 | — | — | — | 服务间契约（Feign 接口 + DTO），**只放接口不放实现** |

★**依赖方向只允许 `服务 → 别人的 *-api`**，绝不允许 `服务 → 服务`。
所以 course 用 `RatingClient`（order 的契约）、order 用 `CourseClient`，Maven 不成环、启动也不互相等。

★2026-10-17 起 `fitness-user` 是**第一个连两个数据库的服务**（MySQL + MongoDB）。
注意它没有破坏上面那条：两个库都归它自己，**跨服务依赖一条都没加**。
"一个服务两个存储"和"两个服务一个库"是完全不同的两件事——后者才是真正的耦合。

接口总量：**对外 78 个（24 个控制器）｜管理端 39 个（14 个）｜服务间 53 个（11 个 `/inner/**`）**。
★2026-10-17 逐条从 `@*Mapping` 数出来的（旧值 75/52 是撤购物车之前抄的，已经对不上）。
这三个数是拿来对账的，不是装饰——改了接口忘了更新它，就说明附 A 那张总表也一定漂了。

## 三、逐服务功能与实现思路

### 3.1 gateway —— 认证与路由

| 功能 | 实现思路 | 检查点 |
|---|---|---|
| 路由 | `/api/<前缀>/**` → `lb://服务名`，`StripPrefix=1` 去掉 `/api`。**按声明顺序取第一条命中**，所以更精确的路由（`/api/seckill/list` 归 course）必须排在通配那条（`/api/seckill/**` 归 order）前面 | 404 先怀疑路由归属，不是控制器 |
| JWT 校验 | 验签 → 解析 `userId/jti` → 透传 `X-User-Id` 给下游 | 下游服务**不自己解 token**，只读头 |
| 令牌白名单 | `login:token:{jti}` 存在才算有效（**fail-close**：查不到就当未登录） | 禁用用户要立即掉线，靠的就是这一层 |
| 白名单匹配 | `AntPathMatcher`（以前用 `String::startsWith`，`/api/admin/**` 这种 glob 永不匹配 → 后台 100% 进不去） | 白名单写精确路径，不写 `/**` 兜底 |
| 拒绝状态码 | 按 `ErrorCode` 映射：`/inner/**` 与越权返 403，鉴权失败才 401 | 401 会触发前端清 token，混用会把登录态搞坏 |

★`/inner/**` 在网关第 1 步**硬拒**任何外部请求。内部接口靠"路径约定 + 网关拦截"保证不外泄，
所以**新增内部接口忘了挂 `/inner/` 前缀 = 直接对外暴露**，这是要盯的红线。

### 3.2 user —— 账号与消息

| 功能 | 实现思路 |
|---|---|
| `POST /auth/login` | 密码登录（★不是验证码登录，短信验证码从未实现）。签发 JWT 时把 `jti` 写进 Redis 白名单，并 `SADD login:user:{userId}` 记下"这个人的所有在线 jti" |
| `POST /user/register` | 手机号唯一索引兜底 |
| `GET/PUT /user/profile` | 改昵称不影响历史内容——因为动态/评论/评价都存了**昵称快照** |
| `PUT /admin/user/status` | 禁用 = 改 `t_user.status`（挡新登录）**+ 批量删该用户所有 jti**（已登录的立即下线）。两件事互补，少做任何一件都有窗口 |
| 站内消息 `GET /message/{list,unread-count}`、`POST /read,/read-all` | 消息由 **RabbitMQ 事件驱动**生成：`ex.notify` 是 topic 交换机，按 `notify.booking / notify.point / notify.community` 三个路由键分发，消费者在 `NotifyEventConsumer` 落 `t_message` |

| 身体记录 `GET /body/metrics`、`POST /body/record`、`GET /body/record/{latest,list}`、`GET /body/trend`、`POST /body/record/delete` | **Mongo `yd_profile.body_record`，一人一天一篇**（D22）。写入是 `upsert(query={userId,recordDate})`，撞 `uk_user_date` 唯一索引就降级成 update 重试一次；★"没测"的字段用 `Update.unset()` 抹掉、**不存 0 也不存 null**；趋势走五段聚合，`match(metric exists)` 那一段专门把缺失日期剔掉，否则折线会连出一条不存在的直线 |
| 健身档案 `GET/POST /body/profile` | **MySQL `t_user_profile`**，主键就是 `user_id`（一人一行 ⇒ 省掉唯一索引，也让"重复建档"从物理上不可能）。写入是"传了才改"：`null` 字段保持原值。★BMI **算出来返回、不落库**——身高或体重一变它就错，能算的不要存 |
| ★为什么这一个功能两个库 | 判据两条：**字段能不能缺**（身体记录常缺 → 文档；档案字段有界 → 表）、**要不要跨人统计**（档案要按目标筛会员 → 关系型；身体记录永远只按 `userId` 取一段 → 文档）。详见 `数据库设计与功能实现说明.md` 4.2.5 |
| ★为什么这些接口**不挂** `@Idempotent` | 保存本身幂等（同一天提交两次 = 同一篇被写两次），唯一索引已经保证不会多出第二篇。加时间窗注解反而会让"用户上午填了下午想改"被拒 3 秒——**幂等注解是防副作用，不是防写** |

★`t_message.msg_type` 的 `INTERACTION` 类型以前一直没有生产者，社区重新上线（切片 K）后才有：点赞、收藏、评论、回复四类通知。

### 3.3 course —— 内容域

| 功能 | 实现思路 | 关键点 |
|---|---|---|
| `GET /course/list` | 条件查询 + 卡片字段（`kind/actions/ratingText/latestFreeText`）全部**后端算** | ★ actions 由"课类型 + 有没有进行中的秒杀"决定，前端自己拼会在秒杀刚结束那几十秒给出过期按钮 |
| `GET /course/detail` | **缓存三件套**：物理 TTL + 随机抖动（防雪崩）、逻辑过期 + Redisson 互斥锁 + 线程池异步重建（防击穿）、空值缓存 2 分钟（防穿透） | ★物理 TTL = 逻辑 × 2 + 抖动。逻辑过期先触发，所以永远不会"提前砸 DB"；物理那一层负责让 key 不无限堆积 |
| 评分/评论数在缓存之外填 | 详情缓存 30 分钟，但"4.8 分 / 12 条"和"共 N 条评论"是新进来就该变的数 | ★缓存对象里**永不含**这两个字段，每次响应前单独取一次。否则就是"评了却看不见" |
| `GET /store/nearby` | Redis GEO：`GEOSEARCH store:geo`，50km 内按距离升序取 20 | ⚠️ 圆心坐标目前是**常量**（`USER_LNG/USER_LAT` 写死），前端没传经纬度。这是待修项，不是设计 |
| 门店启动灌 GEO | `ApplicationRunner` 幂等重建（先删 key 再灌） | GEO 是唯一"启动时重建"的结构，Redis 清了不丢数据 |
| `GET /course/coach/list` | 一条 JOIN（`t_coach × t_coach_course`）查完，★绝不允许"先查关联表拿 id 再循环 selectById" | C 端 VO **不带 phone**（教练手机号是个人信息） |
| `POST /video/progress` | 进度只增不减（`WHERE progress < 新值`）+ 防刷速率校验（增量 > 真实耗时×1.5+15 秒就拒）+ **完课时才发事件，且只有 false→true 那一次** | ★`finished` 列以前永远 0 → 每次上报都发事件 → +30 分反复到账。切片 J 在 UPDATE 里加了 `finished = IF(#{newProgress}>=100,1,finished)` |
| `GET /coupon/list`、`POST /receive`、`GET /my` | 领券两条路径：秒杀券走 Lua（Hash 计数，限库存 + 限领 N 张）、普通券走 `COUNT(*)`（不限库存） | ★**重复预热时不能删 `coupon:got`**，删了就是"领过的人能再领一次" |
| `GET/POST /course/comment` | 两级评论靠 `root_id` 平铺：一级 `root_id=0`，回复 `root_id=所属一级`。读一共两条 SQL（一级一页 + `root_id IN(...)` 捞回复），★不在循环里逐条查 | ★`replyToUser` **不接受前端传值**，服务端从父评论那一行取——前端能传任意字符串，等于允许在课程页伪造"回复 @教练" |
| `/inner/course/batch-detail` | 传的是"课 × 店"的**对**而不是两个列表 | 同一门课在不同店价格窗口不同，拆成两个集合就得做笛卡尔积再筛，语义会丢 |
| 规则文案（策略模式） | `rule/` 包：`RuleScene` + 5 个策略（可售课按次、按不限次、展示课、普通券、秒杀券），工厂按场景取，**同一场景注册两次直接启动失败** | ★规则文案由后端产出，因为"有效期这一句要带门店上下文"，前端算就要多传一次数据、还要维护一份字典 |

### 3.4 order —— 交易与履约

这是最重的一个服务，三条轴都在这里。

| 功能 | 实现思路 | 关键点 |
|---|---|---|
| `GET /booking/preview` | 下单页试算：一次返回四个金额 + 这个份数下手里哪些券可用（含"为什么不可用"）+ `maxQuantity` | ★**只读**，不写库不核销券。用户每改一次份数、每换一张券就重新拉一次——因为"券能不能用"有五条规则（金额门槛 / 券的使用时间窗口 / 课程白名单 / 门店白名单 / 已使用状态），这些规则**只允许有一份**。前端复制一份必然漂成"页面显示可用、点提交报错" |
| `POST /booking/create` | ① 调 `BookingPriceCalculator.quote()` 算价 ② `BookingTxWriter` 一个事务里写订单 + 核销券 ③ 事务提交后再投延迟消息、发通知 | ★试算与成交走**同一个方法**，所以两个金额不可能不一样；券不可用在建单这里才抛异常（试算时它只是给用户看的一句说明）；核销失败 → 那条 insert 一起回滚，库里不留"引用未核销券"的孤儿单 |
| 份数上限 | 上限常量 `MAX_QUANTITY_PER_ITEM` 由 preview 下发成 `maxQuantity`，前端加号到数就禁用 | ★超限时**报错**，不再静默 `Math.min` 截断。以前用户点 20 份、服务端按 10 份建单出票，不报错也不提示——"没报错的错"最难查 |
| `POST /booking/pay` | ① CAS 置 PAID（`WHERE status='UNPAID'`）② **同一事务内出票**（按份数生成 N 张独立凭证）③ 事务成功后发通知 | ★凭证不合并成"一张总次数=N"：退款/过期/展示全按单张走，合并就要支持部分退款，那是第四种复杂度 |
| `POST /booking/cancel` | 只有 `UNPAID` 能取消；已支付走退款任务 | 与 15 分钟超时取消抢同一行，谁先改成功谁说了算（CAS，不需要锁） |
| 超时取消 | 下单时投一条**延迟消息**（`x-delayed-message` 插件，15 分钟）。消费时只判 `status='UNPAID'` | ★**不撤回消息**：用户已付款的话，延迟消息到了影响 0 行，自然什么都不做 |
| `GET /reservation/slots` | 三趟构建整点格子网格：① 门店营业 ∩ 教练工时求可约区间 ② 查该教练当天已占格子（`t_coach_busy`）③ 按课程 `lesson_hours` 做**不可拆分组装**（一节 2 小时的课不能跨"1 小时空格 + 1 小时占用"） | 每个格子带 `reason`：`CLOSED/PASSED/BOOKED/SELF_USED/GROUP_UNAVAILABLE/NO_ENTITLEMENT`，★后端给原因码不给文案 |
| `POST /reservation/create` | **同一本地事务**里写预约单 + 占格子（按开始时间升序逐格 INSERT） | ★升序插入让并发请求以同一顺序拿锁，死锁概率降到最低；撞 `uk_coach_start` 就是"刚被别人约走"（43011） |
| `POST /reservation/cancel` | `WHERE status='BOOKED' AND cancel_deadline > NOW()` | ★"提前 1 小时才能取消"这条规则**固化在列上**（`cancel_deadline` 入库时算好），Java 不计算时间，也就不依赖应用与 DB 时钟一致 |
| 到点结算 | 每分钟扫 `end_time <= NOW() AND status='BOOKED'` → 置 FINISHED + **扣凭证一次** | ★口径：下课才算消费完（不是开课、也不是核销）。取消的走 CANCELED 分支永远进不来，所以"取消不扣次"是免费的 |
| `POST /admin/reservation/verify` | 按 10 位核销码 `WHERE verify_code=? AND status='BOOKED' AND verified_at IS NULL` | ★核销只登记到店，**不改状态、不扣次**。所以点错不会扣掉用户一次课 |
| `EntitlementExpireTask` | 每小时：过期 ACTIVE → EXPIRED；其中**一次都没用过**的把订单推 REFUNDED | 用过一点的剩余不退（D7）。CAS + 带状态条件，重跑安全，不需要 ShedLock |
| `POST /rating/save` | 门槛：该单至少一张凭证且**全部不再是 ACTIVE**（用完或过期）才能评。一单一评（`uk_order` 兜底），可软删 | ★评价写侧全在 `yd_order`，与订单同库同事务 → 零跨服务、零分布式事务 |
| 三张评分统计表 | `t_course_rating_stat / t_store_rating_stat / t_coach_rating_stat`，用 `INSERT ... ON DUPLICATE KEY UPDATE` 增量维护 `sum/count` | ★**贝叶斯分不落库**：`(C*M+sum)/(C+n)` 里 C=20、M=4.5 在 yml，落库就锁死了参数、改一次要刷全表。展示用算术平均，只有排序/优选标签用贝叶斯分 |
| `GET /mine/summary` | 一个 SQL 域内数四件事：订单数、凭证可用数、待上课预约数、可评价单数 | 三张表都在 `yd_order`，所以接口放订单服务，不放 user |

### 3.5 point —— 激励

| 功能 | 实现思路 | 关键点 |
|---|---|---|
| `POST /checkin/do` | ① `INSERT t_checkin_record`（撞 `uk_user_date` = 今天已打过）② Redis 位图 SETBIT ③ 位图从今天的位往低数连续天数 ④ `PointsTxWriter` 事务：流水 + 余额 ⑤ **事务成功后**才 `ZINCRBY` 月榜 + 发通知 | ★**判重从"GETBIT 后 SETBIT"换成唯一索引**：两次 Redis 命令之间有窗口，并发双击会加两次分。<br>★写入顺序的原则一句话：**不可重建的先落库，可重建的最后写缓存**。榜少一分能回填，钱错不得 |
| 位图一人一 key | `point:check:{userId}`，offset = 距基准日（2026-01-01）天数 | ★旧形状 `point:check:{yyyyMM}:{userId}` 数不出跨月连续。基准日是常量、**永远不能改**（改了所有历史位图错位），所以不放进配置 |
| 位图可重建 | key 不存在时用 DB 明细补最近 400 天（`ensureBitmap`） | 不补的后果不是数据错，是"连了 40 天的人显示连续 1 天"——没人报错但用户一定发现 |
| `GET /checkin/calendar` | 直接读 DB 一次范围查询 | ★不逐天 GETBIT 31 次，而且 Redis 被清空时日历不会变空白 |
| 积分入账 | 单独一个 `PointsTxWriter` Bean | ★为什么不用本类的私有方法打 `@Transactional`：Spring 事务靠**代理**生效，同类里 `this.method()` 不走代理，注解写了等于没写。这是最经典的静默失效坑 |
| `POST /point/exchange` | CAS 扣积分（`WHERE balance >= cost`，影响 0 行 = 余额不足）+ 扣库存同事务 | 余额和库存都是"带条件的 UPDATE"，不需要锁 |
| `GET /rank/monthly` | ZSet 实时榜 Top50 + 我在 50 名外时追加真实名次 | 昵称由 Feign **一次批量**补，失败降级"神秘运动者" |
| `GET /rank/history` | 历史月读 `t_rank_archive`（★单表 + `season` 字段，不是每月一表） | 名次用归档时固化的 `rank_no`，**不重算**——结榜那一刻是历史事实 |
| 归档任务 | 每月 1 日 **00:10**（让出十分钟等旧 key 静下来）：读上月 ZSet → 补打卡数与最长连续 → upsert → 给旧 key 设 40 天 TTL | ★`INSERT ... ON DUPLICATE KEY UPDATE` + 主键 `(season,user_id)` = 重跑安全，**不需要分布式锁** |

### 3.6 community —— 内容分发

| 功能 | 实现思路 | 关键点 |
|---|---|---|
| `POST /community/publish` | 昵称/头像**发布时快照**入库；★**只有 `visibility=PUBLIC` 才扇出**到粉丝收件箱（ZADD `feed:inbox:{粉丝}`，score=发布时间，只留最近 1000 条） | FRIEND/PRIVATE 一旦进了别人收件箱就等于公开，**不可逆**。所以这一句 if 是整个可见性设计里最不能省的 |
| `GET /community/feed?tab=recommend` | 热度分 `LOG10(收藏×5 + 评论×3 + 点赞×2 + 浏览×0.2 + 1) / (距今小时数 + 2)^1.5` | ★权重按**用户付出成本**排（点一下 < 写一句 < 收藏）；浏览最廉价最易刷所以只给 0.2；`LOG10` 压量级；`+2` 是新帖保护；`1.5` 是衰减重力<br>★时间用**整小时**取数 → 同一小时内分数完全不变，这就是"翻页不重复"的来处 |
| 推荐池只框近 7 天 | 分数是算出来的、没有索引可用（MySQL 建不了这个表达式索引） | ★不框窗口就是每次请求全表算分再排序 |
| `tab=follow` | 推模式收件箱只当**候选 id 集合**，翻页交给 DB 的 `id < 游标` | ★不在 ZSet 上按 index 翻页：新动态 ZADD 会把成员往后挤，第 2 页必然重复第 1 页末尾那条 |
| `tab=friend` | 拉模式：`author_id IN (互关好友) AND visibility IN (PUBLIC, FRIEND)` | ★"好友"= 互关，用一条**自连接** SQL 现算，**不建 `t_friend` 表**（建了就要在关注/取关时双向同步，同步失败就出现"我显示他是好友、他不显示"） |
| 可见性判定 | 三档各判各的，不写成一个 OR 查询 | `PUBLIC OR (FRIEND AND author IN(互关)) OR author=我` 这种 OR+IN 在 MySQL 里基本用不上索引 |
| 点赞 / 收藏 | **两张表**（不合成带 `type` 的一张）；关系行 + 原子 UPDATE 计数同库同事务；`uk_post_user` 是并发双击的最终防线 | ★合并省一张表，换来唯一键、计数回退、取消动作、"我的"两个 tab 四处都要多一个 type 判断 |
| 评论 | 两级封顶 + `root_id` 平铺；一级分页返回、每条默认带前 2 条回复 + 总数；展开走 `/replies` | ★软删的评论**留占位**（"该评论已被删除"），否则删一条会把整串回复带走。<br>★不匿名：点评论人能进他主页 |
| 浏览量三层 | Kafka 明细（复用 `yd-behavior-event`，不新建 topic）+ Redis Hash 存**未入账增量** + MySQL `view_count` 存账本 | ★刷库**不能用 GET→写库→DEL**（中间新产生的浏览会被 DEL 掉，永久少计），要用 `HINCRBY field -delta` 原子取出 + `view_count = view_count + delta` 入账<br>★计数参与排序就必须去重：`post:viewed:{日期}` 集合按"一人一帖一天"挡，`eventId = postview:帖:人:日` 落库再撞 `uk_event` 兜住并发 |
| 展示时 | `views = 账本 + 未入账增量`（整页一次 HMGET） | 所以"刚看完就 +1"体感是对的，DB 那列晚 30 秒才动没关系 |

### 3.7 behavior —— 埋点

| 功能 | 实现思路 |
|---|---|
| `POST /behavior/report` | 接口本身**不落库**，逐条投 Kafka（key=deviceId → 同设备事件进同一分区、按序消费）。上报路径保持极快 |
| `BehaviorEventConsumer` | 三层幂等：`eventId` SETNX（快）→ `uk_event` 唯一索引（稳）→ 异常只记日志不阻断消费组。`course_click` 额外 `ZINCRBY behavior:hot:course:{yyyyMM}` 喂首页热度榜 |
| ★`props` 全链路（切片 H 补） | 前端传 → 生产者放进消息 → 消费者序列化落 `t_behavior_log.props`（JSON 列）。库里这一列**只写不读**，所以不映射成 Map、不配 TypeHandler。以前整条断了，"从哪个 banner 点进来的"永远答不了 |
| ★手动 ack：**决定不做** | 埋点语义是 append-only + 允许少量丢失，auto-commit + 幂等键已够用；改手动 ack 会带来"何时提交、失败要不要停整个分区"两个新问题而收益为 0 |

### 3.8 admin-server —— 管理端 BFF

| 功能 | 实现思路 | 关键点 |
|---|---|---|
| 登录 | 图形验证码（答案 Redis 存 2 分钟，**取出即删**防重放）→ BCrypt 比对 → 签发管理端 JWT（独立密钥，与用户端不通用） | 菜单在登录响应里一起返回，不是独立接口 |
| RBAC | `@RequireRole("SUPER")` + 拦截器；两个角色 SUPER / OPERATOR | 粒度停在**菜单**级，一期不做按钮级（没有"能看不能改"的真实场景） |
| 操作日志 | `@OperateLog` 切面：参数 JSON 截断、IP、耗时、成功与否，**独立线程池异步落库** | ★日志坏了不能拖垮主流程；队列满就丢 |
| 跨服务聚合 | 订单/凭证/预约三页都要补会员昵称 → 统一走 `MemberNameLoader`（一次 Feign + 失败降级空 Map） | ★三处各抄一份的话，**降级策略会分叉**：一份返回空、一份抛异常，同一个故障三个页面表现不同 |
| 订单详情 | order 给的是"订单 + 平铺凭证 + 平铺预约"，BFF 按 `entitlement_id` 把预约挂到各张凭证下面 | ★展示结构归 BFF，数据关系归服务。归组是界面形状，不是数据归属 |
| 看板 | 三路取数（order 统计 + course 计数 + user 会员数），**每路单独降级**（失败给 0，不白屏） | ★判断标准一句话：失败了用户看到的是"少一个数字"还是"事情没做成但以为做成了"？前者可降级，后者必须抛 |
| 教练删除 | 先问 order"他还有未开始的预约吗"，通过后再让 course 删 | ★跨库前置校验由 BFF **编排**，绝不让 course 反向依赖 order（服务依赖成环的代价远大于多一次调用） |
| 图片上传 | 四道拒绝：后缀白名单 → 魔数校验 → UUID 重命名 → normalize 后判 `startsWith(root)` | ★上传是最容易写出远程代码执行的入口，价值全在拒绝了什么。<br>返回 `{path, url}`：库内存相对路径，换域名/上 CDN 不用刷表 |

## 四、端到端业务流程（检查用）

### 流程 1 · 登录与下线

```
POST /api/auth/login
  → user 服务校验密码 → 签发 JWT（含 jti）
  → Redis: SET login:token:{jti} = userId（TTL=剩余有效期）、SADD login:user:{userId} jti
之后每个请求
  → gateway 验签 → EXISTS login:token:{jti}？不存在直接 401（fail-close）
  → 透传 X-User-Id 给业务服务，业务服务从 UserContext 取，绝不自己解 token
下线
  → 管理端禁用 → 改 status + 删 login:user:{userId} 下所有 jti → 下一个请求就进不来
```
**检查点**：`token-check-enabled=false` 时退回纯无状态 JWT，禁用会失效——这个开关只为"本机没起 Redis 时先联调别的"，演示必须开。

### 流程 2 · 购买（下单页试算 → 建单 → 支付 → 出票）

```
GET  /api/booking/preview?courseId&storeId&quantity&couponRecordId
  └─ quote()：课程快照(一次 Feign) → 可售判定 → 份数归一(超限报错)
              → 券判定 → 原价 / 抵扣 / 实付 → 一次批量拿券列表
     ★页面上那几个数字全部来自这里；改份数、换券都要重新拉
  └─ 顺带**预分配一个 orderNo** 并写 `order:create:token:{userId}:{orderNo}`（TTL 10 分钟，
     value 只是发号时间戳，★不存金额）→ 一起返回给前端。它就是下面 create 要带的令牌

POST /api/booking/create    请求体只有 ID 和用户的选择，没有任何价格字段
  ├─ ★第一步先消费令牌：GETDEL order:create:token:{userId}:{orderNo}
  │     取不到 = 43013"页面已过期或已提交过"。orderNo 不是创建时才生的，
  │     是 preview 就发好的**一次性令牌**——连点两下、超时重发都只有第一次能过
  ├─ 再走一次同一个 quote()                 ← 试算与成交同源，两个金额必然相等
  ├─ 事务：INSERT t_booking(UNPAID) + Feign 核销券   ← 一起成败
  └─ 事务之后：投 15 分钟延迟消息 + 发站内通知        ← 发出去收不回，不放进事务

POST /api/booking/pay       UPDATE ... WHERE order_no=? AND status='UNPAID'
  └─ 同一事务：按份数生成 N 张凭证（valid_until 由该店 valid_type 算）
     ★出票必须与"置 PAID"同事务，否则会出现"付了钱没有凭证"或"没付钱却有凭证"
```

**2026-10-17 撤掉的东西**：`/cart/add`、`/cart/list`、`/cart/checkout` 三个接口、
`t_cart_item` 表、`t_booking.parent_no` 列，以及整组支付/整组取消那两条
`UPDATE ... WHERE parent_no=?`。撤它的理由不是"购物车难做"，而是"多商品合并成一单"
会连带要订单项表、优惠分摊（一张券抵多门课要摊到每项，否则部分退款算不出退多少）、
部分退款的语义、跨门店时一张券只覆盖半个订单的范围冲突。私教课一次买两门是低频动作。
`quantity`（一次买多份 = 出多张凭证）保留——那是出票规则，不是购物车功能。
**检查点**：①付完款立刻 `GET /api/entitlement/mine` 要能看到凭证，这是同事务的唯一证明；
②拿**同一个 orderNo 提交两次**，第二次必须 43013 且 `t_booking` 里只有一行——这就是"手抖只出一张单"的证明；
③提交成功后 Redis 里那个 token key 必须已经消失（`EXISTS` 返 0），还在就是 `getAndDelete` 没用对。

### 流程 3 · 超时取消（延迟消息不撤回）

```
15 分钟后消息到 → UPDATE t_booking SET status='CANCELED' WHERE order_no=? AND status='UNPAID'
  影响 0 行 = 用户已付款 / 已自己取消 → 什么都不做
  影响 1 行 = 退券（Feign course /inner/coupon/refund）+ 发通知
```
**检查点**：这是全项目最漂亮的一条设计——**消费时用状态判等，比撤回消息简单且不会出错**。

### 流程 4 · 预约与履约

```
GET  /api/reservation/slots   三趟构建：门店营业 ∩ 教练工时 → 已占格子 → 按 lesson_hours 不可拆分组
POST /api/reservation/create  同一事务：写预约单 + 按开始时间升序逐格 INSERT t_coach_busy
        撞 uk_coach_start → 43011 "该时段刚刚被预约，请刷新后重试"
POST /api/reservation/cancel  WHERE status='BOOKED' AND cancel_deadline > NOW() → 置 CANCELED + 删占用行
        ★不扣次（取消只是把格子还给别的用户）
[每分钟] ReservationSettleTask  end_time <= NOW() AND status='BOOKED' → FINISHED + consumeOne 扣一次
[每小时] EntitlementExpireTask  过期 ACTIVE → EXPIRED；一次没用过的 → 订单 REFUNDED
```
**检查点**：① 取消后格子必须立即可约（同事务删占用）；② 扣次发生在**下课**，不在开课、不在核销；
③ `t_coach_busy` 一格一行而不是区间行，是把"区间重叠判断"变成"主键冲突判断"，用数据库能力换代码复杂度。

### 流程 5 · 评价与评分

```
POST /api/rating/save  门槛：该单有凭证 && 没有任何一张还是 ACTIVE
  → INSERT t_rating（uk_order 保证一单一评）
  → 同一事务：三条 INSERT ... ON DUPLICATE KEY UPDATE 更新课程/门店/教练统计
     ★教练只在"这条评价确实选了他"时才计入，一单最多计一位
读：GET /api/course/detail → Feign /inner/rating/stats 批量取 sum/count
  → 展示分 = sum/count（算术平均）；排序分 = (C*M + sum)/(C + count) 现算，C/M 在 order 的 yml
```
**检查点**：贝叶斯分**不落库**（参数可调，落库就锁死，改参数要刷全表）；读侧失败降级"暂无评分"，不影响出图。

### 流程 6 · 秒杀

```
[每 30 秒] 扫将要开始的活动 → 先 SET Redis 库存、再把活动 UPDATE ... WHERE status=0 翻开放
   ★顺序保证绝不存在"状态已开放但库存未就绪"的空窗
POST /api/seckill/book（order）
  ① Feign 查进行中活动
  ② 预写排队结果 QUEUEING（前端立刻能轮询）
  ③ Lua 原子：库存 DECR + 一人一单 SISMEMBER/SADD（失败码 1=售罄、2=重复）
  ④ 投 MQ → 消费者建单（DB 侧扣份数 + 写订单），失败回补 Redis 库存
GET /api/seckill/result?seqId  轮询排队结果
```
**检查点**：库存以 Redis 为准、DB `remain` 是账本；`seckill:bought` 集合**是唯一真相且没有 DB 副本**——这是当前仅剩的一处"Redis 清了业务就错"，重预热时删它会放开重复抢，不删它活动换了 id 又是空的。★待补：用订单表重建资格集合。

### 流程 7 · 领券

```
GET  /api/coupon/list          秒杀券显示剩余库存、普通券不显示
POST /api/coupon/receive       @Idempotent 3 秒窗口挡双击
  秒杀券 → Lua：HGET coupon:got:{id} userId 判限领 N 张 → HINCRBY → DECR 库存
  普通券 → COUNT(*) FROM t_user_coupon 判上限（不限库存）
  落 t_user_coupon（uk 兜住"一人一张"那一档）
```
**检查点**：`remain = total - 已发`，是**读时算的账**，不是"库存扣减后剩多少"。★重复预热不能删 `coupon:got`。

### 流程 8 · 打卡与月榜

```
POST /api/checkin/do   INSERT 明细（撞唯一键=今天已打过）→ SETBIT → 数连续 → 事务(流水+余额) → ZINCRBY 榜 → 通知
[每月 1 日 00:10]      读上月 ZSet → 补该月打卡数/最长连续 → upsert t_rank_archive → 旧 key 设 40 天 TTL
```
**检查点**：删掉 `point:check:{userId}` 再打卡，日志里要出现"位图已从 DB 重建"。

### 流程 9 · 社区分发

```
发布 PUBLIC → 扇出 ZADD feed:inbox:{每个粉丝}（只 PUBLIC）
读推荐流  → 算分 + score < 游标（小时桶保证翻页稳定）
读关注流  → ZSet 取候选 id → DB 用 id 游标翻页 → 回表过滤 status=1
读好友流  → 互关集合（自连接）→ author IN(...) AND visibility IN(PUBLIC,FRIEND)

```

## 五、并发防护三档（本项目自己的判据）

★总原则（他定的）：**这是练习项目，不为极端并发上分布式事务/ShedLock/TCC/RedLock/布隆过滤器/限流。**
所以每个写接口只回答一个问题：**它属于哪一档？**

| 档 | 判据 | 手段 | 具体位置 |
|---|---|---|---|
| **必须防** | 错了就是资损或数据打架 | **唯一索引 + 带状态条件的原子 UPDATE（CAS）**，同一本地事务 | 秒杀扣库存(Lua)、抢时段 `uk_coach_start`、支付/取消/扣次(`consumeOne` 的 `SET` 顺序★)、券领取、兑换扣积分、打卡 `uk_user_date`、点赞收藏 `uk_post_user`、**身体记录 `uk_user_date`（Mongo，靠 upsert 撞唯一索引★）** |
| **值得防** | 用户双击/脚本重试会造成重复副作用 | `@Idempotent`（时间窗 SETNX）+ 数据库唯一索引兜底 | 领券 3s、评价 5s、创建预约 5s（★共 3 处；下单不归这一档，见下一行） |
| **值得防·变体** | "同一份意向只能兑现一次"，时间窗不够用 | **一次性令牌**：`GETDEL` 原子消费，用掉即废 | `POST /booking/create` 消费 preview 发的 orderNo（时间窗注解挡不住慢重发，也挡不住"过期页面提交"） |
| **不防** | 低频管理动作、错了重做一次就好 | 直接写，靠唯一索引自然拦 | 配课、配门店、改窗口、启停教练、图片上传、社区评论删除 |

★`consumeOne` 的 `SET` 子句顺序是**必须记的一条**：MySQL 的 SET 从左到右求值，
所以"状态用 CASE 判定"必须写在 `used_times = used_times + 1` **之前**，否则判定拿到的是加过之后的值。

★**已经不存在的一条**：`community:following:{userId}`（切片 K 整条删除）。
它以前"只在关注时写、共同关注却拿它当唯一数据源"，清一次 Redis 共同关注永久为空。
**修掉这类问题的办法常常不是加同步任务，而是让那个事实只有一份。**

★**Mongo 不进这张表**：`yd_profile.body_record` 是用户资产，不是缓存、没有 TTL、也不可由谁重建。
判据就一句——这张表里的 key 要么"丢了能从 DB 重建"、要么"丢了就作废重来一次"；
Mongo 那篇**丢了就是真没了**，所以它属于第六节之外的数据库账本（见 `数据库设计与功能实现说明.md` 4.2.5）。
把缓存和数据混在一张清单里，是"为什么这个 key 敢不设 TTL"问不出答案的开始。

## 九、检查业务流程时最值得盯的十一处

1. **凭证有没有和支付同事务**（流程 2）→ 会不会"付了钱没凭证"。
2. **扣次时机是不是 `end_time`**（流程 4）→ 出现在 `create` 或 `verify` 里扣次就是错的。
3. **`t_coach_busy` 是不是按开始时间升序插入**（流程 4）→ 乱序插入会抬死锁概率。
4. **`consumeOne` 的 SET 顺序**（第五节）→ CASE 判定必须在自增之前。
5. **FOREVER 的每一处过期判断有没有 `IS NOT NULL`** → 漏一处就是常年课被集体误判退款。
6. **判重有没有"先查后写"的窗口** → 打卡、领券、点赞、抢时段，凡是先 SELECT 再 INSERT 都要问一句：并发时靠什么？
7. **缓存里有没有塞进"实时数"**（评分/评论数/位图）→ 有就是"改了却看不见"。
8. **扇出/删除动作有没有把不该公开的东西公开**（社区 `publish` 那句 `if PUBLIC`）→ 隐私是不可逆的。
9. **BFF 里有没有藏业务判断**（占用率标红、成交口径）→ 有就说明放错了层。
10. **`/inner/**` 新接口有没有被外部路径暴露** + 白名单里有没有"配了但没人实现"的死条目。
11. **"没测"有没有被写成 `0`**（流程 10）→ 一旦出现，趋势图上就会凭空多一个"体脂 0%"或"酸痛 0 级"的点，
    而 0 在酸痛这个指标上恰恰是**合法值**（今天不酸），两种含义共用一个数字就再也分不开了。
    同一份数据只能有一种"缺"的写法：Mongo 里靠**字段不存在**，MySQL 档案表里靠 `NULL`。

**已知空位**（不是 bug，是明确没做）：
门店经纬度写死常量（前端不传坐标）｜秒杀资格集合无 DB 副本｜券资格集合无重建任务
｜限流缺位｜社区配图仍是渐变下标（没接上传）｜`soldCount`/`bookedThisWeek`/会员连续天数等跨域派生数一期没给
｜举报与内容审核没做｜管理端"选课程"下拉未过滤 `kind=SALE`｜前后端尚未真实联调（见 4.14）
｜**身体数据没有任何设备来源**（没有手表/体脂秤 API），所以只有手动录入的 8 项，★心率/步数/摄氧量这类"看着更专业"的字段一个都没存——存了就是编数据
｜**Mongo 侧只有一个集合、一条索引、零个跨库事务**：档案和记录之间不需要一致性，因为它们存的是不同的东西
