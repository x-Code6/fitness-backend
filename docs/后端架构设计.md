# 悦动健身 · 后端架构设计（P0 编码依据）

> 状态：设计已确认（2026-10）。本文档是编码阶段的唯一依据，功能范围以 §4 为准。
> 前端参照：`fitness-web`（Mock 接口已按本设计的路径/字段实现，切换真实接口见 §9）。

## 0. 已确认的决策记录

| 决策项 | 结论 |
|---|---|
| 架构形态 | **微服务全套**：Gateway + 5 个业务服务 + common 公共模块 |
| 秒杀交互 | **异步排队 + 轮询**：下单接口立即返回排队号，MQ 异步建单，前端轮询结果（前端秒杀页需小改，见 §10） |
| 第一批范围 | **P0 全核心**（本文档 §4），社区域（community-service）归 P1 |
| 运行环境 | **CentOS VM 部署**：中间件跑 VM 的 Docker Compose；开发期服务可二选一（本机 IDEA 连 VM 中间件 / 全套打包上 VM），演示用全套 VM 部署 |
| 不使用 | Spring Security（用 JWT + 网关过滤器）、Flyway（用 SQL 脚本）、Sentinel（P2 再议） |
| 双 MQ | **RabbitMQ（业务消息）+ Kafka（行为埋点流）**，Kafka 提前纳入 P0：`fitness-behavior` 服务负责埋点接收/消费/热门课程聚合，形成"埋点 → Kafka → 聚合 → 首页推荐"闭环 |

|---|---|---|---|---|

| fitness-user | 8101 | yd_user | 手机号验证码登录（Mock 免校验）、JWT 签发、用户资料 | MySQL、Redis |
| fitness-course | 8102 | yd_course | 课程列表/详情（**缓存三件套**）、门店 GEO、秒杀活动与库存预热、跟练视频与进度上报（完课发 MQ 事件）、inner 名额占用/释放 | MySQL、Redis、RabbitMQ |
| fitness-order | 8103 | yd_order | 普通预约（占名额 + 状态机）、**秒杀**（Lua 原子校验 + MQ 异步建单 + 轮询结果）、模拟支付、取消、**延迟消息自动取消**、WebSocket 预约提醒（P1） | MySQL、Redis、RabbitMQ、Feign→course |
| fitness-community | 8105(P1) | yd_community | 发布动态、**Feed 推模式收件箱**、点赞、关注（P1 一并做，Feed 前提）、发动态加分事件 | MySQL、Redis、RabbitMQ |
| fitness-point | 8104 | yd_point | 每日打卡（**Bitmap**）、积分余额/明细、月度排行榜（**ZSet**）、消费完课/发动态事件加分、消费幂等 | MySQL、Redis、RabbitMQ、Feign→user |
| fitness-behavior | 8106 | yd_behavior | 埋点上报接收（**发 Kafka**）、Kafka 消费落 `t_behavior_log`、热门课程点击榜聚合（Redis ZSet）、热点推荐接口 | MySQL、Redis、Kafka |
| fitness-common | — | — | 统一信封 `Result`、错误码、全局异常、JWT 工具、`@Idempotent` 幂等注解（AOP+Redis）、`@RateLimit` 限流注解（Redisson RRateLimiter）、MQ 消息体定义 | — |

**内部接口约定**：服务间调用统一走 `/inner/**` 前缀，网关**不路由** `/inner/**`（外部无法触达），服务间经 Nacos 直连。

**Feign 调用矩阵**：

```
order  → course：查课程场次余位 / 占名额(原子 UPDATE) / 释放名额
point  → user  ：批量查用户昵称（排行榜展示）
community → user：批量查用户昵称（P1）
其余跨服务交互一律走 MQ 事件（松耦合）：
course(完课) → point；community(发动态) → point；order(占/释名额) 用 Feign 同步（需要实时结果）
```

## 3. 技术栈版本基线

JDK 17 · Spring Boot 3.5.x · Spring Cloud 2025.x · Spring Cloud Alibaba（Nacos 2.x，编码时锁定兼容版本组合）· MyBatis-Plus · Redisson · RabbitMQ（x-delayed-message 插件，复用 lifetools-rabbitmq:3.13-delayed 镜像）· **Kafka（KRaft 单节点，Docker 容器；spring-kafka）** · jjwt · springdoc-openapi · Lombok · validation · Docker Compose。

**双 MQ 场景划分（面试口径）**：业务指令类消息（可靠投递/延迟/死信）走 **RabbitMQ**——秒杀建单、延迟取消、积分事件；行为埋点流（高吞吐 append-only、按设备顺序、可回溯）走 **Kafka**——前端行为上报与热门课程聚合。

统一约定：响应信封 `{code:0, message:'ok', data}`；所有写接口走 validation 参数校验；日志带 traceId（MDC，网关生成透传）。

## 6. Redis Key 设计

| Key | 类型 | 用途 |
|---|---|---|
| `seckill:stock:{activityId}` | String | 秒杀库存（预热写入，Lua 原子 DECR） |
| `seckill:bought:{activityId}` | Set | 一人一单资格（SISMEMBER/SADD 同在 Lua 内） |
| `seckill:result:{seqId}` | String | 排队结果（QUEUEING/SUCCESS:订单号/FAIL:原因），TTL 10min |
| `course:detail:{id}` | String(JSON) | 课程详情缓存，值内嵌 `expireTime` 实现**逻辑过期** |
| `course:empty:detail:{id}` | String | 空值缓存防穿透，TTL 2min |
| `store:geo` | GEO | 门店坐标，GEORADIUS 按距离排序 |
| `point:check:{yyyyMM}:{userId}` | Bitmap | 每月打卡位图，offset = 日-1 |
| `rank:month:{yyyyMM}` | ZSet | 月度积分榜，member=userId |
| `feed:inbox:{userId}` | ZSet | Feed 推模式收件箱，score=发布时间戳（P1） |
| `behavior:hot:course:{yyyyMM}` | ZSet | 课程点击热度榜（course_click 事件 ZINCRBY），首页推荐排序数据源 |
| `idempotent:msg:{msgId}` | String | MQ 消费幂等（SETNX + TTL） |
| `idempotent:api:{userId}:{path}` | String | 接口防重（@Idempotent） |

## 7. MQ 拓扑

| 交换机 | 类型 | 队列 | 路由键 | 用途 |
|---|---|---|---|---|
| `ex.order.seckill` | direct | `q.order.seckill.create` | `seckill.create` | 秒杀异步建单（削峰） |
| `ex.order.delay` | **x-delayed-message** | `q.order.timeout` | `order.timeout` | 15min 未支付自动取消 |
| `ex.course.event` | direct | `q.point.course.finished` | `course.finished` | 完课事件 → 加 30 积分 |
| `ex.community.event`(P1) | direct | `q.point.community.published` | `community.published` | 发动态 → 加 20 积分 |
| （Kafka）`yd-behavior-event` | — | 单 topic，3 分区，key=deviceId | — | 行为埋点流：消费落库 + 热度聚合 |
| 各业务死信 | direct | `q.*.dlq` | — | 消费失败兜底 + 告警日志 |

可靠性约定：生产者 publisher-confirm + 失败落日志表；消费者手动 ack、先查 Redis 幂等（SETNX）再处理、异常 nack 重试 1 次后进死信。

## 8. 关键流程时序

**秒杀（异步排队 + 轮询）**
```
前端 → POST /seckill/book
  order: @RateLimit → @Idempotent → Lua{GET 库存<=0? FAIL : SISMEMBER 已购? FAIL
         : DECR 库存 + SADD 买家} → 生成 seqId，写 seckill:result=QUEUEING
         → 发 MQ(seckill.create, 带 seqId/userId/activityId) → 返回 {seqId}
消费端 → 幂等检查 → 建订单(UNPAID, activity_id 非空, price=秒杀价)
       → 发 15min 延迟取消消息 → seckill:result:seqId = SUCCESS:orderNo
       → 手动 ack；失败 → FAIL:原因 + 恢复库存(Lua INCR) → 进死信
前端 → GET /seckill/result?seqId 每 500ms 轮询，SUCCESS 即跳"我的预约"
```

**15 分钟未支付自动取消**：下单成功即发 `x-delay=900000` 延迟消息 → 消费时重查订单，仍 UNPAID 才执行取消（状态机防并发：`UPDATE ... SET status=CANCELED WHERE id=? AND status='UNPAID'`，影响行数=0 说明已支付）→ Feign 释放名额。

**完课发积分（跨服务事件）**：course 收到进度上报 → 若 progress≥100 且该用户该视频未记录完课 → 写 t_video_progress.finished + 发 `course.finished` 事件（带 eventId 供幂等）→ point 消费 → Redis 幂等检查 → 流水 +30、余额 +30、ZINCRBY 榜单。

**每日打卡**：SETBIT 当月位图 → GETBIT 判重 → BITFIELD 从今天起取 31bit 反推连续天数 → 事务内记流水 + 余额 → ZINCRBY 月榜。

**行为埋点（Kafka 闭环）**：前端 SDK 攒批 → POST /behavior/report（匿名放行，带 deviceId）→ behavior 校验后逐条发 Kafka（key=deviceId，保证同设备事件有序）→ 消费者落 `t_behavior_log`（eventId 幂等）→ `course_click` 追加 `ZINCRBY behavior:hot:course:{yyyyMM}` → 首页调 `/behavior/hot/courses` 取 TopN → 前端按热度重排"推荐课程"。链路价值：埋点 → 流式聚合 → 反哺业务展示。
